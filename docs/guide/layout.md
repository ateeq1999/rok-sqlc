# Generated and scaffolded files

An API project built with rok-sqlc holds three kinds of files, and each
behaves differently when you run `rok-sqlc g` again:

- **Generated** files start with `// @generated by rok-sqlc. Do not edit by
  hand.` Every run rewrites them from the schema and `rok-sqlc.toml`, and a
  run removes one once nothing produces it any more (a stale file). Never
  edit them: change the schema or the configuration and regenerate.
- **Scaffolded** files start with `// Scaffolded once by rok-sqlc; this file
  is yours.` rok-sqlc writes one only when it is absent, and never rewrites
  or removes it, not even under `--force`. From then on it is yours.
- **Your own** files carry neither header. rok-sqlc never writes over them:
  a run that would replace one is refused unless you pass `-f`/`--force`.

## Who owns which file

| File | Kind | Written by |
|---|---|---|
| `rok-sqlc.toml` | scaffolded | `init` |
| `AGENTS.md` | scaffolded | `init` |
| `src/main.rs`, `src/app.rs`, `src/config.rs`, `src/error.rs` | scaffolded | `init` |
| `src/shared/mod.rs`, `src/shared/auth.rs` | scaffolded | `init` |
| `src/shared/response.rs`, `pagination.rs`, `validation.rs`, `tenant.rs`, `health.rs` | generated | `g` |
| `src/db/**` (rows, typed ids, SQL, `pool.rs`, `queries.rs`) | generated | `g` |
| `src/features/mod.rs` | scaffolded | `init` |
| `src/features/generated.rs`, `src/features/README.md` | generated | `g` |
| `src/features/<feature>/` all files but `service.rs` | generated | `g` |
| `src/features/<feature>/service.rs` | scaffolded | `g` |
| `migrations/`, query files, `tests/`, other `shared/` tools | yours | you |

`init` scaffolds the skeleton and generates nothing. `g` generates the data
layer, the shared tools and the features, and scaffolds each new feature's
`service.rs`. The directories follow the configuration: `output` for the
data layer, `api.output` for the features, and `shared/` beside
`api.output`.

## What regeneration does

**A new table** gets a new feature folder, a scaffolded `service.rs`, and a
line in `generated.rs`, which `app.rs` already calls.

**A changed table** gets its generated files rewritten. New endpoints and
changed signatures arrive in `service_api.rs` with working defaults, so your
`service.rs` still compiles unless one of your overrides names something that
changed; the compiler points at it.

**A dropped table** loses its generated feature files and its data-layer
module. Its `service.rs` stays, because it is yours, but `generated.rs` no
longer declares it: move what you need and delete the folder.

**A dropped `[api]` section** removes `db/pool.rs`. Without `api.output` a
run can't know where the features were, so the features and `shared/` files
stay until you delete them.

**A deleted scaffolded file** is written again: `rok-sqlc g` restores a
feature's `service.rs`, and `rok-sqlc init` restores the skeleton's files.
`rok-sqlc g --check` reports a missing scaffolded file, but never its
contents, so your changes never count as drift.

## Building a binary

A binary uses only part of the generated data layer and shared tools, so
rustc warns about the rest (`dead_code`, `unused_imports`). Either allow
those two lints in `Cargo.toml`, as the example does, or declare the modules
in a `lib.rs` and use the library from `main.rs`.
