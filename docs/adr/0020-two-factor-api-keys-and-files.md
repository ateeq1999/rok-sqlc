# Two-factor sign-in, API keys, uploads and avatars in the templates

Until 0.8.0 both templates left eleven contract endpoints unimplemented: two-factor sign-in, API keys, uploads and profile photos. The login answer's `requires_totp` shape was declared but never used, and `avatar_url` was always missing. In 0.8.0 both templates implement them at once, as hand-written features in the generated features' layout, and the generator learns enough about `ALTER TABLE … CONSTRAINT` for the template's own migration to widen an enum. The decisions are B1–B7 of `.scratch/rok-sqlc-0-8/notes/m6-decisions.md`, with the review fixes recorded below; ADR 0018 (the account flows) and ADR 0019 (axum) still hold.

**Both templates, one copy of the rules (B1).** Each feature's `dto.rs` and `service.rs`, and everything in `shared/security/`, `shared/storage/` and `shared/thumbnail.rs`, is byte-identical in the actix and axum templates (the drift test lists them); handlers, routes, the extractors and `app.rs` are per framework. The new features are `two_factor` (`/auth/2fa/*`), `api_keys`, `media`, and the photo routes in `account`. Two-factor started as a block of `auth/service.rs` and became its own feature when that file passed 600 lines: it has its own query module (`queries/two_factor.sql`), and its copies of `TokenResponse` and `MessageResponse`, as `account` keeps its own `UserResponse`, rather than reach into `auth`. The single-use token lifecycle both use (issue, spend, and each purpose's lifetime and message, `policy`) lives in `shared/security/auth_token.rs`.

**Two-factor: TOTP, its secret sealed, its codes keyed (B2).** Codes are RFC 6238 (`totp-rs`: SHA-1, 6 digits, 30-second steps, one step of drift either way), compared in constant time (`subtle`). The secret is stored AES-256-GCM-sealed under `TOTP_ENCRYPTION_KEY` (32 bytes, base64, required and checked at startup like `JWT_SECRET`), with the account's id as associated data, so a sealed secret copied onto another row doesn't open. The last accepted time step is stored and a conditional `UPDATE` spends it, so a code is never accepted twice, even by two requests at once. Ten single-use recovery codes are shown once at enable and stored as HMAC-SHA256 under a key derived from `TOTP_ENCRYPTION_KEY` (an HMAC of a fixed label), so a leaked table can't be checked against guesses without the key; plain SHA-256 was the first design. Decrypted secrets and the derived key are zeroized when dropped (`zeroize`). Setup answers the secret, its `otpauth://` URI and a QR code (an SVG data URI, so no image crate is needed for it); nothing is enforced until enable confirms a code. With two-factor on, the right password answers `{requires_totp, pending_token}`, a 5-minute single-use `two_factor_pending` token; verify takes it with a code or a recovery code, and a wrong code counts toward the same lockout as a wrong password (5 failures, 15 minutes). Disable needs only the current password, because the contract's `DisableTotpDto` has only that field; to make up for it, disabling bumps `token_version`, signing every session out (the caller's included, as a password change does). Enabling and disabling mail a notice.

**Recovery revokes, a change keeps.** A password reset recovers an account someone else may have had, so its transaction revokes every active API key of the account and spends any pending two-factor sign-in, besides bumping `token_version`. A password change keeps the keys: whoever changes the password knew the old one, and a key's owner revokes it explicitly.

**API keys (B4).** A key is `rok_<8>_<32>` (base62); only its 12-character prefix (to recognise it in a list) and its SHA-256 (to look it up) are stored, and the raw key is answered once. It is sent as `Authorization: Bearer rok_…` (told apart from a JWT by the prefix) or as `X-API-Key`, and works wherever a session does: `AuthUser` gains `credential` (`Session` or `ApiKey(scope)`). A `read` key may only `GET`, `HEAD` and `OPTIONS`; anything else is a `403`. No key reaches `/api/v1/auth` or `/api/v1/api-keys` (`403`): signing in, the account flows and managing keys need a session. The path is compared after percent-decoding (until nothing decodes), resolving empty, `.` and `..` segments and lower-casing, so it is never less decoded than what a router matches: a review found that actix's `AuthUser` checked the raw `req.path()` while actix-router routes the decoded path, so `/api/v1/api%2Dkeys` reached the keys with a key. actix now checks the matched path too. Expired or revoked keys, and keys of a disabled or deleted owner, are `401`; `last_used_at` is written at most once a minute. A key acts with its owner's role, an admin's included, with no cap per key; a user has at most 25 active keys (`409`), created under a row lock on the owner so concurrent creates can't pass the limit.

**The storage port and `object_store` (B5).** Features store bytes through `Storage` (`put`, `get`, `delete` by key, the content type kept), in `shared/storage/`, implemented once over `object_store` 0.13: `file://` (the development default, `./storage`), `s3://bucket` (S3 or any S3-compatible store, configured by the `AWS_*` variables) and `memory://`. `object_store` was chosen over the AWS SDK for its size and because one crate covers local files, S3 and memory; 0.13 shares `reqwest` 0.12 with the breach check. Keys are server-generated, and `is_valid_key` keeps any key inside the store. `get` answers whole bytes, not a stream: every upload is capped, and bytes keep the port free of either framework's body type. `AppState::new` opens `STORAGE_URL` (a review found it silently started in memory and only `run` swapped the real store in), so any application built from it stores where it is configured; the tests configure `memory://`.

**Upload safety (B6).** An upload is a raw body of at most `MEDIA_MAX_UPLOAD_BYTES` (10 MiB, `413`). Its type is detected from its bytes (`infer`), never from `Content-Type` or the name, and must be one of `MEDIA_ALLOWED_TYPES` (JPEG, PNG, WebP, GIF, PDF), else `415 unsupported_media_type`, a new code of the wire standard. Bytes are stored first, then the row, and the bytes are deleted if the row fails; delete removes the row, then the bytes, best effort. Content is served with the detected type, `X-Content-Type-Options: nosniff`, a `sandbox` CSP, and `Content-Disposition: attachment` for anything that isn't an image. Files are owner-scoped: another user's is a `404`. Under actix, an upload handler takes `web::Payload` and reads it after its extractors: actix polls a handler's extractors together, so a `web::Bytes` parameter buffered the body while `AuthUser` was still checking the credential against the database, even for a caller then refused. axum runs extractors in order, so its body is already read after `AuthUser`. Both frameworks' plain-text `413` becomes the wire standard's in `shared/body.rs`, with `AppError::too_large` building it.

**Avatars and the decoder's bomb limits (B7).** `PUT /users/me/avatar` takes at most 2 MiB, decodes JPEG, PNG or WebP with `image` under `image::Limits` (8192×8192, 128 MiB of allocation), crops the centre to 256×256 and re-encodes it as JPEG, which drops EXIF and any payload hidden in the original. GIF is not accepted, though the contract's description mentions it: one frame of an animation is not what a user picks. An undecodable or oversized image is a `422`. The photo is stored as `avatars/<random>.jpg`, the old one deleted after the commit, and served publicly at `/api/v1/avatars/<file>` with `Cache-Control: public, max-age=31536000, immutable` (a new photo gets a new name). `avatar_url` is a generated column, `'/api/v1/' || avatar_key`, so the generated `users` feature and the hand-written features answer it with no generator change; the cost is that the `/api/v1/` prefix is written in the schema too.

**The generator follows `DROP` and `ADD CONSTRAINT … CHECK` (B3).** Checks and composite foreign keys now have names, declared or the ones PostgreSQL gives (`<table>_<col>_check`, `<table>_check`, `<table>_<cols>_fkey`, numbered when taken), so `ALTER TABLE … DROP CONSTRAINT` drops a primary key, a unique constraint (and its lookup), a foreign key (and its relationship) or a check (recomputing its column's value list and ranges from the checks that remain), and `ADD CONSTRAINT … CHECK (col IN (…))` adds one. The template's `0003` migration widens `auth_tokens.purpose` this way, and `AuthTokenPurpose` gains `TwoFactorPending`. An added check may also be in `pg_dump`'s form, `col = ANY (ARRAY['a'::text, …])`; `CREATE TABLE` still reads only `IN (…)`, so code generated from existing schemas doesn't change. Dropping a name the model doesn't track (an `EXCLUDE` constraint, PostgreSQL 18's `<table>_<col>_not_null`) first failed the whole table; it now warns, located at its statement, and changes nothing, since those constraints shape no generated code (`IF EXISTS` stays silent). `RENAME CONSTRAINT` fails the table when the old name is unknown or the new one taken, as PostgreSQL does, and warns for a name in the form of an untracked kind (`…_not_null`, `…_excl`).

## Considered Options

- **One shared crate for the templates' common code**: rejected again (ADR 0019); a template is copied and must build alone.
- **The AWS SDK, or one implementation per backend, for storage**: rejected for `object_store`, one crate for local files, S3-compatible stores and memory.
- **Streaming `get`**: rejected; uploads are capped, and bytes keep the port framework-free.
- **Plain SHA-256 recovery codes**: rejected in review for a keyed HMAC; 50 bits of code are guessable offline from a leaked table.
- **Asking for a code to disable two-factor**: the contract's body has only `current_password`; signing every session out on disable covers a stolen session instead.
- **A per-key role cap** (keys never admin): not done; a key is its owner acting from a script, and the owner revokes it.
- **OAuth, passkeys and QR login**: not planned.

## Consequences

- `TOTP_ENCRYPTION_KEY` is required; a template project without it doesn't start.
- `AuthUser` accepts API keys, and has a `credential` field; code matching it exhaustively or building it by hand changes.
- Template migrations `0003_two_factor.sql`, `0004_api_keys.sql` and `0005_avatars.sql` are new; an existing project applies them in order.
- Both templates gain `aes-gcm`, `totp-rs`, `qrcode`, `object_store`, `infer`, `bytes`, `image`, `hmac`, `subtle` and `zeroize`.
- `AppState::new` returns a `Result` and opens `STORAGE_URL`; a test configures `memory://` or swaps a store in with `with_storage`.
- `DROP CONSTRAINT`, which 0.7 refused as an unsupported clause (failing the table), is followed; a name the model doesn't track generates with a warning rather than failing the table.
