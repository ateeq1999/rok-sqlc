# Strict generation by default

rok-sqlc refuses to generate when a table contains unsupported constructs: it writes nothing and exits nonzero, naming the offending table and construct. Generation only proceeds for partially unsupported schemas when `--lenient` is passed, in which case skipped tables are reported as `warning:` lines on stderr and the exit code is 0. We chose strict-by-default because a partially generated output directory that silently lacks resources is a worse failure mode than a loud error; most generators do the opposite, so this records the intent to stop the default from being "fixed" later.

Failure diagnostics are evaluated against the selected scope: with `--resource users`, an unrelated unsupported table neither aborts a strict run nor produces warnings.

The all-skipped case is not a successful lenient run: when every table in scope is unsupported, rok-sqlc still exits nonzero (`all tables are unsupported`), because exit 0 would report success while writing nothing — the footgun this ADR exists to prevent.

A skipped table keeps what an earlier run generated for it. When a table the schema still defines fails (a later migration breaks it), its resource directory is kept byte for byte and `db/mod.rs` keeps declaring it, so the consuming crate still builds against the last version that generated. Those files are not stale: a lenient `--check` reports the failure as a warning but no drift for them. A table the schema no longer defines (dropped, or never created) has no failure, and its files are stale and removed as before. Deleting the last good files of a table that merely failed would turn a warning into a broken build, which is the opposite of what `--lenient` asks for. A strict run that hits the same failure still writes nothing.

Keeping the files is only half of the promise: the rest of the output must still fit them. A kept `models.rs` uses its value-list enums from `types.rs`, a kept `relationships.rs` loads children by its typed id, and a kept `filter.rs` calls its children's filters. So the parser records each failed table's **last good shape**, the model just before the statement that failed it (for a table failed by a check after parsing, such as a managed column with no source of values, its parsed model), with its value lists resolved. The run plans every other file as if the kept tables generated in that shape, but writes none of theirs: `types.rs` still defines their enums, a child's foreign key keeps the typed id, relationships and filters reach them, and `db/mod.rs` keeps `UpdateOutcome` when a kept table is versioned. That shape is what the earlier run generated from, as long as the migrations it saw end before the failing statement, which is the case this ADR is about. A table with no last good shape, because it failed at its own `CREATE TABLE` or its value lists cannot be generated, or whose last good shape uses an enum that no longer generates, is not kept: its files are stale, since planning the rest without them is the only consistent output. The module harness compiles both cases under the lint gate (a kept table with value-list enums, and one a child references).

The other option was to keep the dependent files too (the child's resource and `types.rs`) when a table is kept. It was rejected: the dependents could not pick up their own schema changes until the broken table was fixed, so one failure would freeze unrelated tables, and the set of dependents (relationships, filters, query files, `mod.rs`) is wider than a file list can track.

A statement the SQL parser can't read is treated the same way when rok-sqlc can tell what it alters (0.2). An input that doesn't parse as a whole is read statement by statement, split at top-level semicolons: an unreadable `ALTER TABLE` on a known table (`ALTER COLUMN … SET STATISTICS`, `DROP IDENTITY`, …) fails that table at its `path:line`, so `--lenient` skips it and reads on, while any other unreadable statement still stops the run, at its `path:line`, because its effect on the model is unknown. Since 0.2.1, rok-sqlc reads more of what the parser can't, from the statement's tokens, wherever the effect on the model is known: the split keeps a `BEGIN ATOMIC … END` body in its statement; an `ALTER TABLE` clause that leaves the model as it is (`SET STATISTICS`, `SET STORAGE`, `SET GENERATED`, …) is dropped, and `DROP IDENTITY`/`DROP EXPRESSION` read as `DROP DEFAULT`; functions, procedures, `DO` blocks, and `ALTER`s of indexes, sequences and views (renames followed) are skipped. Only clauses it still can't read fail their table.

## Considered Options

- **Lenient by default** (warn + skip, `--strict` to abort) — rejected: silent partial output is a footgun in CI.
