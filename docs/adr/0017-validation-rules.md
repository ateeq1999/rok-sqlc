# Validation rules for generated APIs: pre-checks answer 422, string rules by VineJS name

A generated API (ADR 0016) answered a duplicate email or a dangling foreign key as `409 conflict` naming a database constraint, and had no way to check a format the schema can't express. Clients want answers they can show next to an input. So in 0.5.0 a generated create or update checks, before it writes, what the database would reject, and answers it as a field's `422 validation_failed`; and `[api.rules]` adds string rules by VineJS's names. The decisions are Q52–Q54 of the 0.4 milestone notes.

**Pre-checks come from the schema, and run on the write's transaction.** `create_in` and `update_in` check, after the owner lock and before the write: every foreign key the body holds (present and not `null`) names a row the caller can see (`exists`), and no other row holds the values of a unique key whose columns the body holds (`unique`). Every failure goes into `FieldFailures` (`shared/validation.rs`) and is answered at once, in the `details` shape of the body's rules: `{"email": [{"code": "unique", "message": "email is already taken"}]}`. They run after the body's own rules (the schema's `length`/`range`, `immutable`, and the string rules), so a body that fails those never queries the database. Each is one `SELECT EXISTS (...)` in the data layer: `read::exists_by_id`, an owned table's `listing::exists_owned`, and `listing::<columns>_taken`.

**"Can see" is the read path's scope, so nothing leaks.** A referenced row counts as missing when it doesn't exist, is soft-deleted, is in another tenant, or, for an owned table, belongs to another caller. A `422 exists` therefore says the same thing as the `404` a `GET` of that row would, and never confirms that another tenant's or caller's row exists. To keep that true, a feature without an owner column still passes the caller to the check when its routes need one (`user` or `admin`), and a feature without a tenant column takes the request's `Tenant` when it references a tenant-scoped table: the service method of that create or update gains `user` or `tenant`, which is why the signature can differ from the feature's other methods. A unique key's tenant and owner columns come from the caller in the same way, so `(tenant_id, name)` and `(owner_id, name)` are checked per tenant or owner and reported on `name`. A unique index on plain columns and one `lower(<column>)` entry compares that column ignoring case; a partial index on `<soft-delete column> IS NULL` counts live rows only, while a full constraint counts soft-deleted rows, as the database does. An update never counts its own row.

**409 → 422 is a breaking change, and the 409 stays as the fallback.** A check and its write are two statements, so a row deleted or a duplicate inserted in between still breaks the constraint, which answers `409 conflict` naming it. The checks don't lock what they read (a `FOR SHARE` on the referenced row or a predicate lock for the unique key would serialize unrelated writes); a client that gets a `409` retries and gets the `422`. Clients that branched on the `409` see a `422` instead, which is why this is 0.5.0, listed under breaking changes to the generated API.

**What still answers 409, or isn't checked:**
- **A public route referencing an owned table.** There is no caller, so the check can only say that the row exists, live, in the tenant: it uses `exists_by_id`, and ownership is the application's to enforce (don't reference owned rows from public routes, or override `create_in`).
- **A reference to anything but the referenced table's whole single-column key**, of the key's own type, and a reference to a tenant-scoped table whose tenant column has another type than the one the route already takes. The constraint decides.
- **A `PATCH` holding only some of a composite key's columns.** The others would have to be read from the row first; the constraint decides.
- **A unique index with any other expression** (`upper()`, `coalesce()`, two `lower()` entries): rok-sqlc doesn't read it as a key at all.
- **Check constraints the rules don't cover**, as before: the database answers them without details.

**String rules take VineJS's names and meanings, or fail the config.** `[api.rules.<table>.<column>]` lists rules (`email`, `minLength(3)`, `{ regex = "..." }`) and transforms (`trim`, `toLowerCase`, `toUpperCase`, `normalizeEmail`), in the order given; transforms run while the body is read, so the stored value is the transformed one. Each rule maps to `validator`'s own (`email`, `ip`) where it means the same, otherwise to a function generated into `dto.rs` calling helpers `shared/validation.rs` holds once. A rule rok-sqlc can't give VineJS's meaning is refused with a clear message rather than approximated: `confirmed`, `sameAs` and `notSameAs` (cross-field, which belong in hand-written request types) and `activeUrl` (DNS during validation). `url` is a port of validator.js's `isURL` defaults, so `example.com` passes as in VineJS (`validator`'s `url` would require a scheme). Where rok-sqlc carries only part of validator.js's data, the difference is documented in the configuring guide: `mobile` and `postalCode` know 16 locales and 7 countries, and `mobile` with no locale tries those 16, not every locale.

## Considered Options

- **Keep `409` and add field details to it.** Rejected: `409` means the request conflicts with the resource's state, and clients already treat `422` as "fix this field". One status for every field-level failure lets a form show them together.
- **Check inside the database (deferred constraints, `ON CONFLICT DO NOTHING ... RETURNING`) and map the violation to a field.** Rejected: one violation surfaces at a time, so a body with a duplicate email and a dangling foreign key needs two round trips; and a constraint's name, not its columns, is all the error carries.
- **Lock what the checks read, so the 409 fallback can't happen.** Rejected: the locks would serialize writes that don't conflict, for a race a retry already handles.
- **Count a row the caller can't see as present (only check existence).** Rejected: a `422` on another tenant's id but a `201` on a random one tells the caller that the other row exists.
- **Approximate rules rok-sqlc can't express exactly** (any locale for `mobile`, a scheme-requiring `url`). Rejected for `url`, which is now ported; kept, and documented, for `mobile` without a locale, which Q54's own example (`phone = ["mobile"]`) uses.

## Consequences

A create or update with foreign keys or unique keys makes one extra query per checked field, on its transaction. Overriding `create_in` or `update_in` in `service.rs` drops the generated checks with the rest of the default, and the override can call the same `repo::` reads and `FieldFailures`.
