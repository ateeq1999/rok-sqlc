# axum as a second framework: one seam, the same wire answers

Until 0.7.0 `rok-sqlc` generated API features only for actix-web, and `init --template axum` answered "unknown template". ADR 0016 promised axum as a second framework against the same contract, and that contract comes from an axum starter. In 0.7.0 a project picks its framework, the generator emits that framework's HTTP edge over code that is otherwise identical, and `templates/axum-api/` mirrors the actix template, account flows included. The decisions are A1–A8 of `.scratch/rok-sqlc-0-7/notes/axum-decisions.md`; the guide covers both frameworks where they differ.

**A project picks one framework (A1).** `[api] framework = "actix" | "axum"`, `actix` by default, so a 0.6 project generates what it did. `rok-sqlc init -f/--framework axum` scaffolds the axum skeleton, and `init --template axum` copies the axum template; `--framework` and `--template` don't combine, since a template has its framework. The extractors are *checked, not inferred*: the API needs its framework's extractor in `extractors` (`actix_web` or `axum`), and `framework = "axum"` with only `actix_web` stops `g` naming what is missing. Inferring the framework from the extractors would make a data-layer setting (which extractors `db/http/` emits, possibly both) decide the API's shape.

**Only the HTTP edge differs (A2).** Per framework: `routes.rs`, `handlers.rs`, the request extractors (`AuthUser`, `AdminUser`, `Tenant`, `ValidatedJson`, `Path`, `Query`, `IfMatch`), the `AppError`-to-response mapping, and the server setup in `main.rs` and `app.rs`. The same for both: `dto.rs`, `model.rs`, `repo.rs`, `service_api.rs`, `service.rs` (ports included), the data layer and the `#[utoipa::path]` annotations, so the OpenAPI document is byte-identical apart from its title. In the generator the seam is one type: `ApiFramework` answers each piece a handler renderer asks for (how a handler takes its service, its path and its query, what it returns, how it answers) and the framework's descriptors (its crate's name, the other framework, the wiring `generated.rs` hands `app.rs`, the Swagger UI feature, the skeleton files). Files whose code differs whole (`routes.rs`, `generated.rs`, `shared/health.rs`, `tenant.rs` and the head of `validation.rs`) are rendered by a function per framework; the rest is rendered once.

**Handlers reach services through `State` and `FromRef` (A3).** The generated `features/generated.rs` declares `Services`, one `Arc<XService>` per feature, built once by `register_services(&pool)`, with `impl FromRef<Services> for Arc<XService>` and `impl FromRef<AppState> for Arc<XService>`. The scaffolded, user-owned `AppState` derives `FromRef` and holds `services: Services`, the pool and the auth keys; a generated handler takes `State(service): State<Arc<UsersService>>`, and a generated router is `Router<AppState>`. A hand-written feature adds its service as an `AppState` field, built once in `AppState::new`, never per request: the axum template's `auth` and `account` are fields, and a test swaps the breach check or the audit trail with `AppState::with_breach` and `with_audit`. Alternatives were one extension per service (untyped, a missing one is a runtime `500`) and a generic `AppState<S>` (every signature names it); `FromRef` keeps the handler's dependency in its type and needs no generics.

**Middleware is tower-http, plus two small pieces of our own (A4).** The axum skeleton and template apply tracing, CORS (same-origin), request ids (`x-request-id`, set and propagated), a 2 MiB body limit (`413`), and a 30-second request timeout. The timeout is `app::time_out`, an axum middleware over `tokio::time::timeout`, not tower-http's `TimeoutLayer`, whose `408` has an empty body: ours answers `408 request_timeout` with the wire standard's body, like every other error. The `/auth` rate limit is the template's own tower `Layer` over `governor`'s keyed GCRA (MIT), with the same `429` and `Retry-After` as actix's middleware; `tower_governor` was not used, as its answers and key extraction aren't ours. The limiter's count and `client_ip` live in `shared/rate_limit/limiter.rs`, byte-identical in both templates; `rate_limit/mod.rs` is the framework's middleware. The peer comes from `ConnectInfo`, which `app::serve` provides through `into_make_service_with_connect_info`; a router served without it counts every client as `0.0.0.0`, so the first such request logs a warning.

**Every request under `/api/v1/auth` counts.** actix wraps the whole `/api/v1/auth` scope in the limit. axum nests the auth routes under `/api/v1/auth` with a fallback, and a method-not-allowed fallback, behind the same limit, so an unknown path or method there is counted and answers the wire standard's `404`. The actix scope's default service gives the same `404` body. `/api/v1/auth/me` (the `account` feature's) is its own route behind the same limiter in both.

**What still differs on the wire.** The answers are the same, statuses, codes and messages included: axum's `Path` and `Query` rejections are reworded to actix-web's (`Path deserialize error: can not parse "abc" to a i64`), and a path rejection that is a wiring bug (a route without the parameters its handler takes) is a `500 internal_error` with its detail logged. What the frameworks add around those answers differs, and is documented rather than hidden: only axum answers `408 request_timeout` (actix-web has no request timeout; put one in your proxy) and sets `x-request-id`; outside `/api/v1/auth`, an unknown route is an empty `404` in both, but a wrong method on a known path is axum's empty `405` and actix-web's empty `404`.

**OpenAPI: the same annotations, no `utoipa-axum` (A5).** The handlers keep `#[utoipa::path]` and the derived `OpenApi` lists them, exactly as for actix; Swagger UI comes from `utoipa-swagger-ui`'s `axum` feature. `utoipa-axum`'s `OpenApiRouter` would derive the paths from the routes, but only for axum, so the two frameworks' documents would be built two ways and could drift; and the document test already compares both against one expected file.

**The axum template mirrors the actix one, checked by a drift test (A6).** `templates/axum-api/` is generated from the same `schema.sql`, passes the same contract test against the same OpenAPI document, and has all of M5's account flows. Each template stays self-contained (a user copies one), so the shared code is copied, and `tests/template_drift.rs` fails when a framework-independent file differs between them: `migrations/`, `queries/`, `src/shared/security/`, `src/shared/mail/`, `src/shared/rate_limit/limiter.rs`, the generated features' `dto.rs`, `model.rs`, `repo.rs`, `service.rs` and `service_api.rs`, and the hand-written `auth` and `account`'s `dto.rs` and `service.rs`. Making those copies identical moved two things in the actix template: password hashing runs on `tokio::task::spawn_blocking` (not `actix_web::web::block`), which needs tokio's `rt` feature, and `AuthService` derives `Clone`.

**Generator tests and `check-arch` know the framework (A7).** `tests/api-app-axum` is generated from `tests/api-app`'s migrations with `framework = "axum"`, and both fixtures run the same suites (`tests/api-suite/`), each through a small adapter that sends a request its framework's way; they assert the same wire answers and the same OpenAPI document. `check-arch`'s rule 1 names the project's framework crate (`actix_web` or `axum`), and the other framework's crate is a `rule-1` violation everywhere but the data layer, whose `extractors` may serve both: ``src/features/notes/service.rs:32: rule-1: `actix_web::HttpResponse`: the project uses axum (`[api] framework`), so nothing but db/ may use actix_web``.

**Versions (A8).** axum 0.8, tower-http 0.6, tokio with `rt-multi-thread`, `macros`, `signal`, `net` and `time`. The server stops with `axum::serve(...).with_graceful_shutdown`, and the template's mail sender runs under `tokio::spawn`, stopped by the same signal after requests in flight finish.

## Considered Options

- **A trait over frameworks in the generated code** (one handler body, an adapter per framework): rejected, as generated code would gain an abstraction users must learn, and each framework's idioms (`web::Data` and `HttpResponse` against `State` and `IntoResponse`) read naturally only on their own.
- **A shared crate for the templates' common code**: rejected, as a template is copied into the user's project and must build alone; the drift test keeps the copies identical instead.
- **Inferring the framework from `extractors`**: rejected (see A1).
- **`utoipa-axum`'s router and `tower_governor`**: rejected (see A4 and A5).

## Consequences

- An actix project's generated output is unchanged; only `features/README.md` and the scaffolded `AGENTS.md` word the wiring the same way for both frameworks.
- `check-arch` flags the other framework's crate outside `db/`, which a 0.6 project mixing both would now see.
- Every framework-specific piece of the generator is reached through `ApiFramework`; a third framework would add a variant and its renderers, not new `match`es elsewhere.
- Two templates means two copies of the shared code, held together by the drift test, which names the file that drifted.
