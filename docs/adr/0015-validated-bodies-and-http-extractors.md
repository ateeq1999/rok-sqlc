# Validated bodies and HTTP extractors

An API built on the generated code takes create inputs and update patches as JSON, and should reject a bad body before any statement runs, with an answer a client can act on field by field. rok-sqlc already knows many of the rules (a `VARCHAR(80)` column holds at most 80 characters), so it generates them, and it generates the extractors that apply them for axum and actix-web. Both are opt-in, and the extractors are generated into the output rather than shipped as a crate.

**Rules come from the schema, on the `validator` crate.** `derive = ["serde", "validate"]` adds `validator::Validate` to every create input and update patch, with rules derived from the schema: `VARCHAR(n)`/`CHAR(n)` gives `length(max = n)`, counted in characters as PostgreSQL counts them. A single-column `CHECK` against a literal gives a rule too: a comparison or `BETWEEN` gives `range`, and `char_length(col)`/`length(col)` compared with a literal gives `length`. Every other `CHECK` stays the database's alone. Each rule carries an English message naming the column (`"name must be at most 80 characters"`) and validator's stock code (`length`, `range`). `NOT NULL`, enums, and value lists are not rules: the Rust types already reject a missing field or an unknown label while deserializing. A typed id over text gets `validator::ValidateLength`, and a typed id over an integer gets `validator::ValidateRange`, each delegating to the value inside, so a key column and the foreign keys using its id keep their `length` or `range` rule. A `NUMERIC` column's range is, as a limitation rather than a choice, a `custom` rule calling a function generated next to the input (`balance_in_range`), still with the code `range` and with `range`'s `min`/`max` params (`exclusive_min`/`exclusive_max` for a strict bound): `validator`'s `range` needs `ValidateRange` on the field's type, and the orphan rule forbids implementing validator's trait for `rust_decimal::Decimal` in the consuming crate. A typed id over `NUMERIC` gets no range rule. `validate` without `serde` fails the run. `validator` was chosen over generated plain-Rust `validate()` methods because a hand-written request type, which already uses `validator` in Rok's apps, then goes through the same extractor as a generated input.

**Extractors are generated.** `extractors = ["axum", "actix_web"]` (which requires `validate`) generates `db/http/`, with a module per framework (and reserves the module name `http`, only then): `db::http::axum::ValidatedJson<T>` and `db::http::actix_web::ValidatedJson<T>`, for any `T: DeserializeOwned + Validate`, including hand-written request types. A body is a **validated body** only after it deserializes and passes every rule. Otherwise the extractor rejects with `BodyRejection`, defined once in `db/http/mod.rs` and re-exported by each framework's module:
- `Malformed { message }`, answered `400` with code `MALFORMED_BODY`, for bad JSON syntax, a missing or wrong `Content-Type`, or a body that can't be read;
- `TooLarge`, answered `413` with code `PAYLOAD_TOO_LARGE` and one message from `db/http/mod.rs`, for a body over the framework's own limit: axum's `DefaultBodyLimit` or actix-web's `JsonConfig` limit (both 2 MiB by default in axum 0.8 and actix-web 4);
- `ValidationFailure(validator::ValidationErrors)`, answered `422` with code `VALIDATION_FAILED`, for a failed rule, and for well-formed JSON that doesn't fit the type (a missing field, a wrong type, an unknown label). A body that doesn't fit holds one error under `__all__` with the code `deserialize` and serde's message, and is answered with that message and no `details`.

The extractors build on the frameworks' own JSON extractors, `axum::Json<T>` and `web::Json<T>`, so each framework's settings apply: axum's `DefaultBodyLimit`, and actix-web's `JsonConfig` limit and `Content-Type` predicate. Each framework's module classifies that framework's rejection (`JsonRejection`, `JsonPayloadError`) into a `BodyRejection`, and takes a parse error's message from serde's own `serde_json::Error`, never from the framework's text, through the shared `BodyRejection::from_serde`, which classifies it by serde's `Category`. axum's data and syntax errors wrap serde's error in `serde_path_to_error`'s, whose message adds a field path actix-web lacks and whose `source()` skips serde's error, so the axum module downcasts to it and takes the error inside. The same body then gets the same status, code, and message from both frameworks. What each framework accepts as JSON still follows its own rules: axum takes only `application/json` and `application/*+json`, while actix-web also takes any `*/json` or `*/*+json` (`text/json`, say) and whatever its `JsonConfig` predicate allows.

Both are answered in the Rok error envelope, `{"success": false, "error": {"message", "code", "details"?}}`, where `details` is validator's own serialization of the errors (`{"name": [{"code": "length", "message": "…", "params": {…}}]}`). `BodyRejection` is public, so an app that wants another body matches on it instead of parsing JSON again. Only JSON bodies are covered: query strings, forms, search filters, and query-file parameter structs are not validated. The `{success, data, meta}` response envelope is a separate decision, not made here.

## Considered Options

- **A companion crate (`rok-sqlc-web`) the generated code depends on.** Rejected: generated code has never needed a rok-sqlc runtime crate (ADR 0013), and a small module the user owns, reads, and can edit beats a dependency whose release cycle is tied to the generator's.
- **Generated plain-Rust `validate()` methods, with no `validator` dependency.** Rejected: one extractor could not then take both generated inputs and the hand-written, `validator`-based request types Rok's apps already have.
- **Leave extractors to each app.** Rejected: every app would rewrite the same two extractors and the same envelope, and malformed bodies would keep going through per-app `JsonConfig` handlers in different shapes.
- **Flattened `details` (`{"name": ["…"]}`).** Rejected: existing clients read validator's shape, and its `params` let a client phrase its own message.
- **Reading the body as bytes and parsing it in the generated code.** Rejected: it gave the same messages, but bypassed `JsonConfig` and its `Content-Type` predicate on actix-web. Taking serde's error out of each framework's rejection gives the same messages while each framework's settings apply.
- **Per-field `details` for deserialization errors through `serde_path_to_error`'s path.** Deferred: the type system already narrows the case down, and actix-web has no path to match it.

## Consequences

`VARCHAR(n)` lengths and simple `CHECK`s, which the parser dropped before, are now kept on the model. The consuming crate depends on `validator` (with its `derive` feature), on `serde_json`, and on the framework it lists, and with axum on `serde_path_to_error` (already one of axum's), to reach serde's error. The generated `mod.rs` names them.

> **Superseded in part by ADR 0016 (0.4.0):** the error body becomes `{"error": {"code", "message", "details"?}}` with snake_case codes (`validation_failed`, `payload_too_large`, `bad_request`), the wire standard shared by every generated API.
