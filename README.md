# rok-sqlc

Write SQL, get typed Rust. rok-sqlc reads your PostgreSQL migrations and
annotated query files and generates plain [SQLx](https://github.com/launchbadge/sqlx)
code: row structs, typed ids, CRUD, typed search, relationship loaders, and
one function per query you write. The generated code is ordinary Rust you
commit and read. There is no runtime crate and no macro magic, and you don't
need a database to generate it.

**SQL in:**

<!-- source: docs/examples/quickstart/queries.sql -->
```sql
-- name: ActiveProductsInCategory :many
SELECT id, sku, name, price
FROM products
WHERE category_id = $1 AND status = 'active'
ORDER BY name, id;
```

**Rust out** (in `src/db/queries.rs`):

<!-- source: docs/examples/quickstart/src/db/queries.rs -->
```rust
/// A row returned by `active_products_in_category`.
#[derive(Debug, Clone, PartialEq, sqlx::FromRow)]
pub struct ActiveProductsInCategoryRow {
    /// The `id` column.
    pub id: ProductId,
    /// The `sku` column.
    pub sku: String,
    /// The `name` column.
    pub name: String,
    /// The `price` column.
    pub price: rust_decimal::Decimal,
}

/// Runs the `ActiveProductsInCategory` query (`:many`).
pub async fn active_products_in_category<'e, E>(
    executor: E,
    category_id: CategoryId,
) -> Result<Vec<ActiveProductsInCategoryRow>, sqlx::Error>
where
    E: sqlx::PgExecutor<'e>,
```

From the schema alone, every table also gets a typed `get_by_id`, unique-key
lookups, `list`, `count`, `create`, partial `update`, `delete`, a typed
`search` with keyset pagination, and loaders for the relationships its
foreign keys imply.

Every code sample in this README was generated by rok-sqlc from the example
crates in [`docs/examples/`](docs/examples/), and a test keeps the two in
sync.

> **Status:** 0.3.0, PostgreSQL and SQLx 0.9 only.
> See [Limitations and roadmap](#limitations-and-roadmap).

## Install

Prebuilt binaries for Linux, macOS, and Windows (x86_64 and ARM64) are
attached to every [GitHub release](https://github.com/ateeq1999/rok-sqlc/releases).
The install scripts pick the right one, check its SHA-256 checksum, and put
`rok-sqlc` on your machine.

**Linux and macOS** (installs to `~/.local/bin`):

```sh
curl -fsSL https://raw.githubusercontent.com/ateeq1999/rok-sqlc/main/install.sh | sh
```

**Windows** (PowerShell; installs to `~\.rok-sqlc\bin` and adds it to your
user `PATH`):

```powershell
irm https://raw.githubusercontent.com/ateeq1999/rok-sqlc/main/install.ps1 | iex
```

To pin a release or choose the directory, pass
`sh -s -- --version v0.3.0 --to /usr/local/bin` to `install.sh`, or set
`ROK_SQLC_VERSION` and `ROK_SQLC_INSTALL_DIR` (both scripts read them).
The Linux binaries are statically linked against musl, so they run on any
distribution.

**From source** with Cargo:

```sh
cargo install rok-sqlc
```

To track unreleased changes, install from the repository instead:
`cargo install --git https://github.com/ateeq1999/rok-sqlc rok-sqlc`.

There are two Rust version floors:

- **The tool** needs Rust 1.88 or newer.
- **The generated code** targets SQLx 0.9, so the crate that uses it needs
  Rust 1.94 or newer (SQLx 0.9's minimum).

The generated `db/mod.rs` lists the dependencies your crate needs. It names
only the SQLx features and crates the schema actually uses:

<!-- source: docs/examples/quickstart/src/db/mod.rs -->
```rust
// The generated code requires these dependencies in the consuming crate
// (SQLx 0.9 needs Rust 1.94 or newer):
//   sqlx = { version = "0.9", features = ["runtime-tokio", "postgres", "derive", "uuid", "chrono", "rust_decimal"] }
//   uuid = "1"
//   chrono = "0.4"
//   rust_decimal = "1"
```

So the quickstart crate's `Cargo.toml` has:

<!-- source: docs/examples/quickstart/Cargo.toml -->
```toml
[dependencies]
sqlx = { version = "0.9", features = ["runtime-tokio", "postgres", "derive", "uuid", "chrono", "rust_decimal"] }
uuid = "1"
chrono = "0.4"
rust_decimal = "1"
```

`serde_json` (for `JSON`/`JSONB` columns) and `serde` (with
[`derive = ["serde"]`](#configuration)) show up in the list when they are
needed.

## Quickstart

The complete crate is in [`docs/examples/quickstart`](docs/examples/quickstart).

**1. Write migrations.** A directory of migrations is read in filename order,
and `*.down.sql` files are skipped. Later migrations can `ALTER` earlier
tables:

<!-- source: docs/examples/quickstart/migrations/0001_catalog.sql -->
```sql
CREATE TYPE product_status AS ENUM ('draft', 'active', 'archived');

CREATE TABLE categories (
    id         BIGSERIAL PRIMARY KEY,
    name       TEXT NOT NULL UNIQUE,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE products (
    id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    category_id BIGINT NOT NULL REFERENCES categories (id),
    sku         TEXT NOT NULL UNIQUE,
    name        TEXT NOT NULL,
    price       NUMERIC(12, 2) NOT NULL,
    status      product_status NOT NULL DEFAULT 'draft',
    tags        TEXT[] NOT NULL DEFAULT '{}',
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

<!-- source: docs/examples/quickstart/migrations/0002_product_description.sql -->
```sql
ALTER TABLE products ADD COLUMN description TEXT;
```

rok-sqlc never runs your migrations. Apply them with whatever tool you
already use, such as `sqlx migrate run` or `psql`.

**2. Write queries** for anything the generated CRUD doesn't cover. See
[`queries.sql`](docs/examples/quickstart/queries.sql) and
[Writing query files](#writing-query-files).

**3. Point rok-sqlc at them** with a `rok-sqlc.toml` (optional; flags work too):

<!-- source: docs/examples/quickstart/rok-sqlc.toml -->
```toml
schema  = ["migrations/"]
queries = ["queries.sql"]
output  = "src/db"
```

**4. Generate:**

```sh
rok-sqlc g
```

That is the same as
`rok-sqlc generate --schema migrations/ --queries queries.sql --output src/db`.
It writes:

<!-- tree: docs/examples/quickstart/src/db -->
```text
db/
├── categories/
│   ├── filter.rs
│   ├── mod.rs
│   ├── models.rs
│   ├── read.rs
│   ├── relationships.rs
│   └── write.rs
├── mod.rs
├── products/
│   ├── filter.rs
│   ├── mod.rs
│   ├── models.rs
│   ├── read.rs
│   ├── relationships.rs
│   └── write.rs
├── queries.rs
├── schema.rs
├── search.rs
└── types.rs
```

**5. Call it.** Declare the module (`pub mod db;`) and pass an executor
first: `&pool`, or `&mut *tx` to run several calls in one transaction. The
transaction boundary is always yours.

<!-- source: docs/examples/quickstart/src/lib.rs -->
```rust
    // Every generated function takes an executor first: here, the pool.
    let tools = db::categories::write::create(
        pool,
        NewCategory {
            name: "Tools".into(),
            created_at: None,
        },
    )
    .await?;

    // Several calls in one transaction: pass `&mut *tx` instead.
    let mut tx = pool.begin().await?;
    let hammer = db::products::write::create(
        &mut *tx,
        NewProduct {
            id: None,
            category_id: tools.id,
            sku: "HAM-1".into(),
            name: "Claw hammer".into(),
            price: Decimal::new(1999, 2),
            status: Some(ProductStatus::Active),
            tags: None,
            created_at: None,
            description: None,
        },
    )
    .await?;
    let patch = UpdateProduct {
        price: Some(Decimal::new(1799, 2)),
        description: Some(Some("16 oz, fibreglass handle".into())),
        ..UpdateProduct::default()
    };
    db::products::write::update(&mut *tx, hammer.id, patch).await?;
    tx.commit().await?;
```

Commit the generated code. Regenerate whenever a migration or query file
changes, and check for drift in CI (see [CI with `--check`](#ci-with---check)).

## What gets generated

Each generated file starts with `// @generated by rok-sqlc. Do not edit by hand.`
rok-sqlc overwrites only files that carry that header. It refuses to replace
any other file unless you pass `-f/--force`. When a table, query file or
other source disappears, a later run removes its generated files (the stale
files). A table that is still in the schema but skipped by `--lenient` is not
gone: its files stay as they are.

### Per table: a resource module `db/<table>/`

| File | Contents |
|---|---|
| `models.rs` | The typed id (`ProductId`) or key struct, the row struct (`Product`), the create input (`NewProduct`), and the update patch (`UpdateProduct`). |
| `read.rs` | `get_by_id`, `exists_by_id`, a `get_by_<columns>` lookup per unique key, `list` and `list_page` (ordered by primary key), `count`, `search`, `search_after`. |
| `write.rs` | `create`, `update`, `delete` (and `restore`/`delete_permanently` with soft delete, `attach`/`detach`/`sync` on join tables). |
| `filter.rs` | The search filter (`ProductFilter`) and sort keys (`ProductSortKey`). |
| `relationships.rs` | A `load_<name>` loader per relationship, and `get_with_<name>` joined reads for to-one relationships. |

A table without a primary key gets `create`, `list` and `count` only. `search`
needs at least one sortable column, and `search_after` needs a primary key.
`filter.rs` exists only when one of them does, and `relationships.rs` only
when the table has relationships.

**Typed ids.** A single-column primary key gets its own type, which is used
for that column, for every foreign key that references it, and by every
function that takes the key. Passing a `CategoryId` where a `ProductId` is
expected is a compile error:

<!-- source: docs/examples/quickstart/src/db/products/models.rs -->
```rust
/// A row of the `products` table.
#[derive(Debug, Clone, PartialEq, sqlx::FromRow)]
pub struct Product {
    /// The `id` column.
    pub id: ProductId,
    /// The `category_id` column.
    pub category_id: CategoryId,
    /// The `sku` column.
    pub sku: String,
    /// The `name` column.
    pub name: String,
    /// The `price` column.
    pub price: rust_decimal::Decimal,
    /// The `status` column.
    pub status: types::ProductStatus,
    /// The `tags` column.
    pub tags: Vec<String>,
    /// The `created_at` column.
    pub created_at: chrono::DateTime<chrono::Utc>,
    /// The `description` column.
    pub description: Option<String>,
}
```

A composite primary key gets a key struct instead (`OrderItemKey`, with a
`key()` accessor on the row). A foreign key to a table outside the run keeps
its raw type. An enum primary key's typed id wraps the enum
(`PriorityNoteId(pub types::TicketPriority)`). Like the enum, it is neither
`Ord` nor `Display`. Two tables whose struct names agree (`user` and `users`)
both define `UserId`. A file that would import both, or an imported id named
like one of the file's own items, fails the run. So does any other pair of
imported items of one name, such as the row structs and filters of `category`
and `categories`. Rename one table under [`[modules]`](#rok-sqlctoml), or
rename or opt out the relationship that needs the import under
[`[relationships]`](#rok-sqlctoml).

**Create inputs and update patches.** `NewProduct` leaves out generated
columns (serial, identity, `GENERATED`); a serial column is `NOT NULL` in the
row, on or off the primary key. A column with a default becomes an
`Option`, and `None` lets the database default apply. `UpdateProduct` makes
every column optional: `None` leaves the column unchanged, and for a
nullable column `Some(None)` sets it to `NULL`. An empty patch issues no
`UPDATE` and returns the current row.

<!-- source: docs/examples/quickstart/src/db/products/write.rs -->
```rust
pub async fn update<'e, E>(
    executor: E,
    id: ProductId,
    input: UpdateProduct,
) -> Result<Option<Product>, sqlx::Error>
where
    E: sqlx::PgExecutor<'e>,
```

**Lookups.** Each unique key (a unique constraint, or a unique index on plain
columns) gets a lookup. Text keys are borrowed:

<!-- source: docs/examples/quickstart/src/db/products/read.rs -->
```rust
pub async fn get_by_sku<'e, E>(executor: E, sku: &str) -> Result<Option<Product>, sqlx::Error>
where
    E: sqlx::PgExecutor<'e>,
```

**Typed search.** The filter has a list of typed conditions per column, and
they are combined with `AND`. Numbers, decimals, dates, times and typed ids
take `Ordered<T>` (`Eq`, `Ne`, `Lt`, `Le`, `Gt`, `Ge`, `Between`, `In`,
`NotIn`). Text columns take `Text` (`Eq`, `Ne`, `In`, `NotIn`, `Contains`,
`StartsWith`, `EndsWith`, matched literally). Booleans, UUIDs and enums take
`Equality<T>`. Each nullable column also gets an `*_is_null` check. Sorting
goes through the `ProductSortKey` allowlist, and every value is bound, so no
caller string ever reaches the SQL text:

<!-- source: docs/examples/quickstart/src/lib.rs -->
```rust
    let filter = ProductFilter {
        price: vec![Ordered::Lt(Decimal::new(5000, 2))],
        name: vec![Text::Contains("hammer".into())],
        ..ProductFilter::default()
    };
    let cheap = db::products::read::search(
        pool,
        filter,
        Sort::asc(ProductSortKey::Price),
        Page::first(20),
    )
    .await?;
```

`search` breaks ties by primary key, so pages are stable. `Page` and `Limit`
clamp page sizes to `1..=MAX_PAGE_SIZE` (500). `search_after(executor, filter,
after, limit)` does keyset pagination in primary-key order: pass the last key
you saw.

**Relationships.** Each foreign key between two tables generated together
gives a belongs-to on the child (`category_id` gives `category`) and a has-many
on the parent, named after the child module (`products`). If the foreign key
column is unique, the parent gets a has-one instead. A `parent_id`
self-reference gives `parent` and `children`. A join table (two `NOT NULL`
foreign keys that together form a unique key) relates its two tables
many-to-many, and its `write.rs` gains `attach`, `detach` and `sync`.

A loader takes rows you already fetched and loads one relationship for all of
them in a single `= ANY($1)` query, which avoids the N+1 pattern:

<!-- source: docs/examples/quickstart/src/db/products/relationships.rs -->
```rust
pub async fn load_category<'e, E>(
    executor: E,
    rows: &[Product],
) -> Result<HashMap<CategoryId, Category>, sqlx::Error>
```

<!-- source: docs/examples/quickstart/src/lib.rs -->
```rust
    let categories = db::products::relationships::load_category(pool, &cheap).await?;
    for product in &cheap {
        let category = &categories[&product.category_id];
        println!("{} ({})", product.name, category.name);
    }
```

To-many loaders return a `Vec` for every input key, empty when nothing is
related. A to-one relationship also gets a joined read that fetches the row
and its related row in one query:

<!-- source: docs/examples/quickstart/src/db/products/relationships.rs -->
```rust
pub async fn get_with_category<'e, E>(
    executor: E,
    id: ProductId,
) -> Result<Option<ProductWithCategory>, sqlx::Error>
```

The search filter gets a field per relationship, which is rendered as an
`EXISTS` subquery, so rows never repeat. For a to-many relationship it means
"at least one related row matches":

<!-- source: docs/examples/quickstart/src/db/categories/filter.rs -->
```rust
    /// Matches rows with at least one of their `products` (`products` rows) matching this filter.
    pub products: Option<Box<ProductFilter>>,
```

To rename or opt out of an inferred relationship, use
[`[relationships]`](#configuration). Two relationships of one table with the
same name fail generation, and the error names both.

### Shared modules

| File | Contents |
|---|---|
| `mod.rs` | Declares every module and lists the dependencies to add. Holds `UpdateOutcome` when a table has a version column. |
| `schema.rs` | `SCHEMA_SQL`: a verbatim snapshot of the input schema. It is never executed. |
| `search.rs` | `Page`, `Limit`, `Sort`, `Direction`, the condition types, and `MAX_RELATIONSHIP_DEPTH`. |
| `types.rs` | A Rust enum for each enum type and each value-list column, keeping its exact database labels. |
| `session.rs` | `set_tenant` and `set_user`, when the conventions name a setting. |
| `queries.rs` or `queries/` | One function per annotated query. |
| `http/` | With `extractors`: `BodyRejection`, the error body (`ErrorBody`), and a `ValidatedJson<T>` per framework (`axum.rs`, `actix_web.rs`). |

<!-- source: docs/examples/quickstart/src/db/types.rs -->
```rust
/// The `product_status` enum type.
#[derive(Debug, Clone, Copy, PartialEq, Eq, Hash, sqlx::Type)]
#[sqlx(type_name = "product_status")]
pub enum ProductStatus {
```

`nullable`, `schema`, `search`, `session` and `types` are reserved module
names, as are `queries` when you pass query files and `http` when you set
`extractors`. A table that would generate one of those modules fails with an
error that says so.

**Code quality.** Every public item is documented. Generated code passes
`#![deny(missing_docs)]`, `cargo clippy -- -D warnings` and a fixed set of
pedantic lints (see [ADR 0013](docs/adr/0013-generated-code-quality-bar.md)),
and it is rustfmt-clean. It never forces your crate to relax its lints.

**Serde.** With `derive = ["serde"]` (or `-d serde`), rows, typed ids
(transparent), key structs, enums (by database label), inputs, patches,
joined-read structs (`ProductWithCategory`), query rows and parameters,
filters (`ProductFilter`), sort keys, and the `db::search` conditions and
`Sort` derive `Serialize` and `Deserialize`, so an API can take a search as
JSON. In a patch, an absent field leaves the column alone and `null` sets it
to `NULL` (`{"note": null}` is `note: Some(None)`); serializing skips the
absent fields. A filter field left out of the JSON adds no condition, and
condition, direction, and sort-key variants are snake_case
(`{"price_cents": [{"ge": 400}]}`, `{"key": "price_cents", "direction": "desc"}`). Without
`derive`, generated code doesn't mention serde. SQLx's `PgInterval` and
`PgTimeTz` implement no serde traits, so with serde a table with an
`INTERVAL` or `TIME WITH TIME ZONE` column (which would also reach its
filter), or a query row or parameter struct holding one, fails the run with
an error naming it.

**Validation.** `derive = ["serde", "validate"]` (or `-d serde -d validate`)
adds `validator::Validate` to create inputs and update patches, with rules
taken from the schema, and `extractors = ["axum", "actix_web"]` (or
`-e axum`) generates a `ValidatedJson<T>` extractor per framework
(see [Validated bodies and HTTP extractors](#validated-bodies-and-http-extractors)).
`validate` without `serde`, or `extractors` without `validate`, fails the run.

## Writing query files

A query file holds SQL statements, each starting with a `-- name:` line:

```text
-- name: <Name> :<mode>
-- param: $<n> <name> <RustType>     (optional, repeatable)
-- column: <name> <RustType>        (optional, repeatable)
<one SQL statement>
```

The name becomes the function name in snake_case. Other full-line comments
are dropped.

| Return mode | Runs | Returns |
|---|---|---|
| `:one` | `fetch_one` | the row; no row is `sqlx::Error::RowNotFound` |
| `:maybe_one` | `fetch_optional` | `Option<row>` |
| `:many` | `fetch_all` | `Vec<row>` |
| `:exec` | `execute` | `()` |
| `:execrows` | `execute` | `u64`, the number of affected rows |

**Parameter types are inferred only from positions that settle them.** These
are:

- a comparison, `IN`, `BETWEEN` or `LIKE` against a known column;
- `= ANY($n)`, which takes a slice;
- an `INSERT … VALUES` position, an `UPDATE … SET` target, or
  `ON CONFLICT … DO UPDATE SET`;
- `LIMIT`/`OFFSET` (`i64`);
- an explicit cast to a supported type, including an enum type
  (`$1::product_status` takes `types::ProductStatus`, and
  `$1::product_status[]` a slice of them).

A placeholder anywhere else fails generation. The error names the fix, a
`-- param:` override.

**Keys keep their typed ids.** A parameter typed by a primary key or foreign
key column takes that table's typed id, and so does a result column taken
straight from one, as in `ActiveProductsInCategory` at the top
(`category_id: CategoryId`, `id: ProductId`). A parameter compared with two
different ids falls back to the plain type, and so does any computed
expression.

Text parameters are taken as `&str` (`&CurrencyId` for a text key) and
arrays as slices. A query with more than three parameters takes a
`{Name}Params` struct instead:

<!-- source: docs/examples/quickstart/queries.sql -->
```sql
-- name: UpsertProductPrice :one
INSERT INTO products (category_id, sku, name, price)
VALUES ($1, $2, $3, $4)
ON CONFLICT (sku) DO UPDATE SET price = EXCLUDED.price
RETURNING *;
```

<!-- source: docs/examples/quickstart/src/db/queries.rs -->
```rust
pub async fn upsert_product_price<'e, E>(
    executor: E,
    params: UpsertProductPriceParams,
) -> Result<super::products::models::Product, sqlx::Error>
```

**Result columns are resolved against the schema.** rok-sqlc infers `*`,
`t.*`, plain and qualified columns, aliases, and `COUNT(…)` (`i64`). The
outer side of a `LEFT`/`RIGHT`/`FULL` join becomes `Option`. A result that is
exactly a table's columns, such as the `RETURNING *` above, reuses that
table's row struct. A single column decodes as a scalar. Anything else gets
a `{Name}Row` struct.

Any other expression needs an alias and a `-- column:` override, and a
parameter rok-sqlc can't type needs a `-- param:` override:

<!-- source: docs/examples/quickstart/queries.sql -->
```sql
-- name: SearchProductNames :many
-- param: $1 pattern String
-- column: display_name String
SELECT sku, upper(name) AS display_name
FROM products
WHERE lower(name) LIKE lower($1)
ORDER BY sku;
```

<!-- source: docs/examples/quickstart/src/db/queries.rs -->
```rust
pub async fn search_product_names<'e, E>(
    executor: E,
    pattern: &str,
) -> Result<Vec<SearchProductNamesRow>, sqlx::Error>
```

**More rules:**

- `WITH` queries work: each CTE is treated as a table.
- An `ON CONFLICT (cols)` target must be one of the table's unique keys, and
  `ON CONFLICT ON CONSTRAINT name` must name its primary key or a unique
  constraint: the declared name, or PostgreSQL's default for an unnamed one
  (`products_pkey`, `products_sku_key`). Like PostgreSQL, a default name
  another relation of the schema already takes (a table, a constraint, an
  index, a sequence, or a view) gets a number (`products_pkey1`). A unique
  index is no constraint, so PostgreSQL doesn't accept its name there.
- A query is exactly one statement. To run several, call several functions
  on `&mut *tx`.
- The SQL is embedded verbatim and bound positionally. It is not checked
  against a database.
- One query file generates `db/queries.rs`. A directory (its `*.sql` files)
  or several `--queries` inputs generate `db/queries/<file stem>.rs`, one
  module per file. Stems must be snake_case Rust identifiers.
- Conventions never rewrite query files: your SQL runs exactly as written.

## Conventions and the `rok` preset

A convention says what a column means in every table that has it. All
conventions are **off by default**. Turn them on in the `[conventions]`
section of `rok-sqlc.toml` or the JSON payload; they have no flags. The
complete example is in [`docs/examples/conventions`](docs/examples/conventions):

<!-- source: docs/examples/conventions/rok-sqlc.toml -->
```toml
[conventions]
preset = "rok"
```

| Key | `rok` preset | Effect on tables that have the column |
|---|---|---|
| `tenant_column` | `organization_id` | Every function takes the tenant right after the executor and adds `organization_id = $tenant` to every statement. The column is left out of inputs, patches, search filters, and sort keys. |
| `tenant_setting` | `app.organization_id` | Generates `db::session::set_tenant`, for row-level security policies. |
| `user_setting` | `app.user_id` | Generates `db::session::set_user`, for audit triggers. |
| `soft_delete_column` | `deleted_at` | `delete` sets it, `restore` clears it, and `delete_permanently` removes the row. Reads skip deleted rows, and filters get `include_deleted`. It must be a nullable `TIMESTAMP`/`TIMESTAMPTZ`. |
| `managed_columns` | `["updated_at", "row_version"]` | Left out of create inputs and update patches, but kept in rows. The database maintains them. |
| `version_column` | `row_version` | `update` takes `expected_version` and returns `UpdateOutcome` (optimistic concurrency). The column is always managed. |
| `primary_key_ids` | off | `"uuid_v4"`, `"uuid_v7"`, `"ulid"` or `"cuid2"`: the generated code makes new primary keys (see below). |

Each explicit key overrides the preset's value. An empty string turns a
single-column convention off (`version_column = ""`), and
`primary_key_ids = "none"` turns key generation off.

`primary_key_ids` applies to tables whose primary key is one `UUID` column,
or with `"ulid"` also one text column; `"cuid2"` applies to one text column
only and leaves `UUID` keys alone. Their typed id gets a constructor
(`EventId::generate()`), and `create` takes the id as an `Option`. `None`
inserts a new id made in Rust, even when the column has a database default:

| Value | Key type | Value made | Dependency |
|---|---|---|---|
| `uuid_v4` | `UUID` | `uuid::Uuid::new_v4()` | `uuid` with its `v4` feature |
| `uuid_v7` | `UUID` | `uuid::Uuid::now_v7()`, ordered by creation time | `uuid` with its `v7` feature |
| `ulid` | `UUID` | `uuid::Uuid::from(ulid::Ulid::new())` | `ulid` with its `uuid` feature |
| `ulid` | text | `ulid::Ulid::new().to_string()`, 26 characters | `ulid` |
| `cuid2` | text | `cuid::cuid2()`, 24 characters | `cuid` 2 |

The generated `mod.rs` lists these dependencies too.

With the preset, the inputs leave out the tenant, managed and soft-delete
columns:

<!-- source: docs/examples/conventions/src/db/invoices/models.rs -->
```rust
pub struct NewInvoice {
    /// The `id` column.
    /// `None` applies the column default.
    pub id: Option<InvoiceId>,
    /// The `number` column.
    pub number: String,
    /// The `total` column.
    pub total: rust_decimal::Decimal,
    /// The `status` column.
    /// `None` applies the column default.

```

`update` is scoped to the tenant and versioned:

<!-- source: docs/examples/conventions/src/db/invoices/write.rs -->
```rust
pub async fn update<'e, E>(
    executor: E,
    organization_id: OrganizationId,
    id: InvoiceId,
    expected_version: i64,
    input: UpdateInvoice,
) -> Result<UpdateOutcome<Invoice>, sqlx::Error>
```

<!-- source: docs/examples/conventions/src/lib.rs -->
```rust
    let mut tx = pool.begin().await?;
    // For row-level security policies and audit triggers.
    db::session::set_tenant(&mut tx, org).await?;
    db::session::set_user(&mut tx, user).await?;

    // The tenant comes right after the executor, on every function.
    let invoice = db::invoices::write::create(
        &mut *tx,
        org,
        NewInvoice {
            id: None,
            number: "INV-001".into(),
            total: Decimal::new(25_000, 2),
            status: None,
        },
    )
    .await?;

    // Optimistic concurrency: the update applies only at the version read.
    let patch = UpdateInvoice {
        status: Some(InvoiceStatus::Paid),
        ..UpdateInvoice::default()
    };
    let outcome =
        db::invoices::write::update(&mut *tx, org, invoice.id, invoice.row_version, patch).await?;
    match outcome {
        UpdateOutcome::Updated(paid) => assert_eq!(paid.row_version, invoice.row_version + 1),
        UpdateOutcome::NotFound => println!("deleted meanwhile"),
        UpdateOutcome::VersionConflict => println!("changed meanwhile; reload and retry"),
    }

    // Soft delete: reads skip the row until it is restored.
    db::invoices::write::delete(&mut *tx, org, invoice.id).await?;
    let hidden = db::invoices::read::get_by_number(&mut *tx, org, "INV-001").await?;
    assert!(hidden.is_none());
    db::invoices::write::restore(&mut *tx, org, invoice.id).await?;
    tx.commit().await
```

The database keeps managed columns up to date: in the example, a
[trigger](docs/examples/conventions/migrations/0002_touch_row.sql) sets
`updated_at` and bumps `row_version`. A managed column that is `NOT NULL` with
no `DEFAULT` (and not identity or generated) needs a `BEFORE INSERT` trigger
on its table, since inserts leave it out; without one, the table fails with a
`path:line` error. Trigger function bodies are not read.

A unique key that includes the tenant
column drops it from the lookup's name, so `UNIQUE (organization_id, number)`
gives `get_by_number`. A tenant column's foreign key is never treated as a
relationship.

## Validated bodies and HTTP extractors

An API takes create inputs and update patches as JSON, and should reject a
bad body before any statement runs. Two opt-in keys do that with the rules
the schema already holds
(see [Validated bodies and HTTP extractors](#validated-bodies-and-http-extractors)).

<!-- source: docs/examples/validated-api/rok-sqlc.toml -->
```toml
derive = ["serde", "validate"]
extractors = ["axum", "actix_web"]
```

`validate` derives `validator::Validate` (validator 0.21) on every create
input and update patch, with a rule for each column the schema constrains.
From this table:

<!-- source: docs/examples/validated-api/migrations/0001_members.sql -->
```sql
CREATE TABLE members (
    id BIGSERIAL PRIMARY KEY,
    name VARCHAR(80) NOT NULL CHECK (char_length(name) >= 1),
    handle VARCHAR(30) NOT NULL UNIQUE,
    age INTEGER CHECK (age BETWEEN 13 AND 130),
    balance NUMERIC(12, 2) NOT NULL DEFAULT 0 CHECK (balance >= 0),
    bio TEXT
);
```

the create input gets:

<!-- source: docs/examples/validated-api/src/db/members/models.rs -->
```rust
pub struct NewMember {
    /// The `name` column.
    #[validate(length(
        min = 1,
        max = 80,
        message = "name must be between 1 and 80 characters"
    ))]
    pub name: String,
    /// The `handle` column.
    #[validate(length(max = 30, message = "handle must be at most 30 characters"))]
    pub handle: String,
    /// The `age` column.
    #[validate(range(min = 13, max = 130, message = "age must be between 13 and 130"))]
    pub age: Option<i32>,
```

| Schema | Rule |
|---|---|
| `VARCHAR(n)`, `CHAR(n)` (and `CHARACTER [VARYING](n)`) | `length(max = n)`, counted in characters as PostgreSQL counts them |
| `CHECK (char_length(col) >= n)`, with `character_length` or `length`, any comparison | `length(min = n)` (or `max`); with a declared length, the tighter bounds, and `equal` when they meet |
| `CHECK (col >= n)`, `>`, `<=`, `<`, the literal on either side, `BETWEEN a AND b`, an `AND` of these, on an integer or float column | `range(...)`. A strict bound on an integer becomes inclusive (`> 0` is `min = 1`); on a float it stays strict (`exclusive_min`) |
| the same on a `NUMERIC` column (`Decimal`, which `range` can't compare, and which the orphan rule keeps from implementing validator's `ValidateRange`) | `custom(function = "<field>_in_range", code = "range")`, a function generated next to the input, whose error carries `range`'s `min`/`max` params |
| a typed id over text | `impl validator::ValidateLength<u64>` on the id, so a length rule applies through it, also on foreign keys |
| a typed id over an integer | `impl validator::ValidateRange<i64>` (the id's integer type) on the id, so a range rule applies through it, also on foreign keys |

Each rule has an English message naming the column and validator's code
(`length` or `range`). A patch field is checked only when it is present, so
an absent field or `null` passes. Every other `CHECK`, `NOT NULL`, enums and
value lists are not rules: the database or deserialization already enforces
them. A typed id over `NUMERIC` gets no range rule.

`extractors` (which needs `validate`) generates `db/http/`: `mod.rs` holds
the shared `BodyRejection` and the error body, and `axum.rs` and
`actix_web.rs` each hold a `ValidatedJson<T>` extractor for any
`T: DeserializeOwned + Validate`, a generated input or patch or a
hand-written request type. The handler runs only for a validated body:

<!-- source: docs/examples/validated-api/src/lib.rs -->
```rust
    async fn create_member(
        State(pool): State<PgPool>,
        ValidatedJson(input): ValidatedJson<NewMember>,
    ) -> Result<Json<Member>, StatusCode> {
        let member = crate::db::members::write::create(&pool, input)
            .await
            .map_err(|_| StatusCode::INTERNAL_SERVER_ERROR)?;
        Ok(Json(member))
    }
```

The actix-web handler is the same, with `crate::db::http::actix_web::ValidatedJson`,
and needs no `JsonConfig` error handler:

<!-- source: docs/examples/validated-api/src/lib.rs -->
```rust
    async fn create_member(
        pool: web::Data<PgPool>,
        ValidatedJson(input): ValidatedJson<NewMember>,
    ) -> actix_web::Result<web::Json<Member>> {
        let member = crate::db::members::write::create(pool.get_ref(), input)
            .await
            .map_err(ErrorInternalServerError)?;
        Ok(web::Json(member))
    }
```

Any other body is answered with the wire standard's error body
(`{"error": {"code", "message", "details"?}}`, ADR 0016), the same on both
frameworks:

| The body | Status | `code` | `details` |
|---|---|---|---|
| no JSON `Content-Type`, bad JSON syntax, or unreadable | `400` | `bad_request` | none |
| over the framework's size limit | `413` | `payload_too_large` | none |
| JSON that doesn't fit the type (a missing field, a wrong type, an unknown label) | `422` | `validation_failed`, with serde's message | none |
| breaks a validation rule | `422` | `validation_failed` | validator's errors by field |

`{"name": "", "handle": "ada", "age": 7}` is answered `422` with:

<!-- source: docs/examples/validated-api/tests/error_body.rs -->
```json
{
  "error": {
    "code": "validation_failed",
    "message": "the request body failed validation",
    "details": {
      "name": [
        {
          "code": "length",
          "message": "name must be between 1 and 80 characters",
          "params": { "min": 1, "max": 80, "value": "" }
        }
      ],
      "age": [
        {
          "code": "range",
          "message": "age must be between 13 and 130",
          "params": { "min": 13, "max": 130, "value": 7 }
        }
      ]
    }
  }
}
```

The extractors read the body through `axum::Json` and `web::Json`, so each
framework's settings apply: axum's `DefaultBodyLimit`, and actix-web's
`JsonConfig` limit and `Content-Type` predicate (actix-web's `PayloadConfig`
limit does not apply to JSON). Both limits default to 2 MiB (axum 0.8,
actix-web 4); set the same limit on both to answer a large body the same way.
A body over it gets `413` and `"the request body is over the size limit"`
from either. A parse error's message is serde's own, taken from inside each
framework's rejection, never the framework's text (axum's adds a field
path), so both frameworks give the same messages. What counts as a JSON
`Content-Type` is still each framework's call: axum takes
`application/json` and `application/*+json`, actix-web also `text/json` and
anything its `JsonConfig` predicate allows. `BodyRejection`
(`Malformed { message }`, `TooLarge` or
`ValidationFailure(validator::ValidationErrors)`) is public, with `status()`
and `body()`, so an app that wants another response can match on it;
`BodyRejection::from_serde` and `db::http::validated(body)` apply the same
rules outside a handler. Only JSON bodies are covered: query strings, forms,
and query-file parameters are not validated. `db/mod.rs` names the
`validator`, `axum`, `serde_path_to_error` (axum wraps serde's error in it)
and `actix-web` dependencies to add. The complete crate is in
[`docs/examples/validated-api`](docs/examples/validated-api).

## Configuration

Options come from four layers. The most specific wins:
**flags > JSON payload (`-j`) > `rok-sqlc.toml` > defaults**. A list (such as
`schema`, `queries`, `derive` or `extractors`) replaces the lower layer's list whole and is
never appended to. `[conventions]` keys, `[relationships]` entries,
`[modules]` entries and `[api]` keys and table entries merge one by one.

### `rok-sqlc.toml`

Without `-c`, rok-sqlc looks for `rok-sqlc.toml` in the current directory and
then in each parent, like Cargo does. Paths in the file are relative to the
file. Unknown keys are errors, so a typo can't silently do nothing. This is
every key:

<!-- config-reference -->
```toml
schema   = ["migrations/"]   # a path or a list: SQL files or migration directories
queries  = ["queries/"]      # a path or a list: query files or directories
output   = "src/db"          # the default
resource = "products"        # add this table to the generated ones; rarely useful in a file
derive   = ["serde", "validate"]  # extra derives for generated types; "validate" needs "serde"
extractors = ["axum", "actix_web"]  # validated-body extractors to generate; need "validate"

[conventions]                # all off unless set; see "Conventions"
preset             = "rok"
tenant_column      = "organization_id"
tenant_setting     = "app.organization_id"
user_setting       = "app.user_id"
soft_delete_column = "deleted_at"
managed_columns    = ["updated_at", "row_version"]
version_column     = "row_version"
primary_key_ids    = "uuid_v7"   # or "uuid_v4", "ulid", "cuid2", "none"

[relationships.invoices]     # by table, then by inferred relationship name
created_by_user  = "author"  # rename: load_author, get_with_author, filter field author
approved_by_user = false     # opt out, together with the other side

[modules]                    # by table: generate it as another module
"audit.users" = "audit_users"  # db::audit_users, with AuditUser and AuditUserId

[api]                        # generated actix-web API features (ADR 0016); off without `output`
output          = "src/features"  # needs derive = ["serde", "validate"] and extractors with "actix_web"
db_path         = "crate::db"     # the default: where the generated data layer is
prefix          = "/api/v1"       # the default URL prefix
search_endpoint = true            # POST /search with per-field filters; off by default
openapi         = true            # the default: utoipa schemas for the OpenAPI document
exclude         = ["audit_log"]   # tables with no API feature

[api.skip]                   # by table: endpoints to leave out
invoices = ["list", "get_one", "create", "update", "remove"]
users    = ["search", "restore", "lookups", "relationships"]

[api.routes]                 # by table: route base, starting with `/` and unique
users = "/members"           # default: `/` and the kebab-case module name

[api.access]                 # by table: who may call; "user" (AuthUser) is the default
products = "public"
invoices = "user"
users    = "admin"           # AdminUser

[api.owner]                  # by table: a UUID NOT NULL column scoping rows to the caller
invoices = "created_by"

[api.hidden]                 # by table: columns left out of responses; not key columns
users = ["password_hash"]

[api.immutable]              # by table: set on create, never by `PATCH`; not key, owner,
users = ["email"]            # tenant or managed columns

[api.search]                 # by table: text columns the list's `q` matches
products = ["name", "sku"]

[api.sort]                   # by table: number, date, time or text columns `sort` takes
products = ["name", "price", "created_at"]
```

`[api]` configures the generated API features (ADR 0016). Without `output`
(or `-a`), every other `[api]` key is ignored. Its single keys and
`exclude` layer like the top-level keys; its table-keyed sections merge by
table. A table key is the table's SQL, schema-qualified or module name. Each
table it names must be generated and each column must exist, or the run
fails naming the key, the table and the column (`api.owner.invoices`).
With `output`, a run also generates `db/pool.rs` in the data layer
(`PoolSettings`, `init_pool`, `check_health`) and the shared tools in
`shared/`, the directory beside `output`: `response.rs`, `pagination.rs`,
`validation.rs`, `tenant.rs` and `health.rs`. `rok-sqlc init` scaffolds
`shared/mod.rs`, which declares them. Each table but join tables and
`exclude`d ones gets an API feature in `output/<module>/`, whose list reads
go in the data layer's `<table>/listing.rs`; `output/generated.rs` declares
the features and `output/README.md` maps which files are generated and
which (`service.rs`) are yours. Generated files there and in `shared/` are
removed once stale. With `openapi` on (the default), every type a feature
exposes derives utoipa's `ToSchema` (or `IntoParams` for a query string),
as do the data layer's typed ids, enums, sort keys and search conditions
inside them; each handler carries `#[utoipa::path]`, `generated.rs` holds
`GeneratedApiDoc`, and the data layer's `mod.rs` names the `utoipa` and
`utoipa-swagger-ui` dependencies. With `openapi = false` the generated
output is exactly as without the document: nothing mentions utoipa. The
scaffolded files `init` wired the document into are yours to edit (see
the OpenAPI guide).

A feature's handlers take the caller as `AuthUser` (`user`) or `AdminUser`
(`admin`), from the scaffolded `shared/auth.rs`, so no valid token is a
`401` and a caller who isn't an admin a `403`; a `public` feature takes
none. An owned table (`[api.owner]`) can't be `public`: its service methods
take the `AuthUser`, every read and write is scoped to the caller's id
(another caller's row is a `404`), and `create` sets the owner, which
neither body holds. A hidden column (`[api.hidden]`) stays in both bodies
but never appears in a response, and no `[api.search]` or `[api.sort]`
entry may name it. An immutable column (`[api.immutable]`) is in the
create body but not the update body: a `PATCH` naming it answers `422`
(detail code `immutable`), and the document leaves it out of `UpdateXDto`.
The data layer's `UpdateX` keeps it for your own code (a verified email
change). A key, owner, tenant or managed column can't be immutable.

`[modules]` renames a table's module, and its row struct, typed id and key
struct follow the new name. That's how same-named tables of two schemas
(`core.users` and `audit.users`) both generate. A key is the table's
schema-qualified name or its SQL name. A key that names no table, or a name
that isn't a snake_case Rust identifier, fails the run.

`[relationships]` entries are checked against the whole schema. An unknown
table or relationship, an invalid name, or a rename that collides fails with
the entry's name (`relationships.invoices.created_by_user`). `true` is an
error, not a no-op.

### JSON payload

`-j/--json` takes the same keys as JSON. Pass it inline
(`-j '{"output":"src/db"}'`), from a file (`-j @config.json`), or from stdin
(`-j -`). Its paths are relative to the current directory. The payload
layers over `rok-sqlc.toml` and doesn't turn discovery off.

```json
{
  "schema": ["migrations/"],
  "output": "src/db",
  "derive": ["serde", "validate"],
  "extractors": ["axum"],
  "conventions": { "preset": "rok", "version_column": "" }
}
```

### Flags

The command is `generate`, or `g` for short (`rok-sqlc g`). The `help`
command prints the help (`rok-sqlc help generate`). `init` (`i`) starts an API
project (see [Starting an API project](#starting-an-api-project-rok-sqlc-init))
and takes only the project directory. `check-arch` (`a`) checks an API
project's architecture (see [Checking the
architecture](#checking-the-architecture-rok-sqlc-check-arch)) and takes
only `-c` and `-l`.

| Flag | Meaning |
|---|---|
| `-s`, `--schema <PATH>` | A schema file, or a directory of migrations read in filename order (`*.down.sql` skipped). Repeat it to combine inputs. |
| `-q`, `--queries <PATH>` | A query file (`db/queries.rs`) or a directory (`db/queries/<stem>.rs`). Repeatable. |
| `-o`, `--output <DIR>` | The output directory. Default: `src/db`. |
| `-r`, `--resource <TABLE>` | Generate this table (SQL or module name) and regenerate every resource already generated in the output directory, so they and `db/mod.rs` stay current. Tables not generated yet stay ungenerated. |
| `-c`, `--config <FILE>` | Read this config file instead of discovering `rok-sqlc.toml`. |
| `-j`, `--json <PAYLOAD>` | The JSON payload: inline, `@FILE`, or `-` for stdin. |
| `-d`, `--derive <NAME>` | Add a derive to generated types (`serde`, or `validate`, which needs `serde`). Repeatable. |
| `-e`, `--extractor <FRAMEWORK>` | Generate a validated-body extractor for `axum` or `actix_web` (needs `validate`). Repeatable. |
| `-a`, `--api-output <DIR>` | Generate actix-web API features into this directory (`api.output`; needs `-d serde -d validate -e actix_web`). |
| `-n`, `--dry-run` | Print what would be written, removed or refused, and touch nothing. |
| `-k`, `--check` | Write nothing. List missing, changed and stale files, and exit 1 if there are any. |
| `-f`, `--force` | Overwrite existing files that rok-sqlc did not generate. |
| `-l`, `--lenient` | Skip unsupported tables and queries with warnings instead of failing. |
| `-h`, `--help` | Print help and exit 0. |
| `-V`, `--version` | Print the version and exit 0. |

`--dry-run`, `--check`, `--force` and `--lenient` are flags only, because
they describe a run rather than a project. A run with no schema (no
`--schema` and no `schema` key) is a usage error. Errors exit with code 1.

## Generated APIs

With `[api] output` set, rok-sqlc generates an actix-web API on top of the
data layer: one **API feature** per table, with routes, thin handlers,
request and response bodies, and a service where business rules go. It
follows one architecture. The [API guide](docs/guide/index.md) covers it
from the first command to production:

- [Getting started](docs/guide/getting-started.md): from `rok-sqlc init`
  (or `init --template actix`) to a running API and Swagger UI;
- [Configuring API features](docs/guide/configuring.md): every `[api]` key
  and the conventions that shape the API;
- [Architecture guidelines](docs/guide/architecture.md): the layout, the
  rules `check-arch` enforces, services, transactions and ports;
- [Generated and scaffolded files](docs/guide/layout.md): which files are
  rok-sqlc's, which are yours, and what regeneration does to each;
- [Customizing the generated API](docs/guide/customizing.md): overrides,
  ports and hand-written features;
- [The wire standard](docs/guide/wire-standard.md): every status, error
  code, body and header;
- [The OpenAPI document](docs/guide/openapi.md): what is generated, your

- [Testing an API](docs/guide/testing.md), [Deploying](docs/guide/deploying.md),
  [After a schema change](docs/guide/after-a-schema-change.md) and
  [Troubleshooting](docs/guide/troubleshooting.md).

The workflow is three commands: `rok-sqlc init` scaffolds the application
skeleton once, `rok-sqlc g` generates `src/db/`, `src/shared/` and
`src/features/` from your migrations, and `rok-sqlc check-arch` checks the
rules in CI. The complete project the guide's samples come from is
[`docs/examples/api`](docs/examples/api). Its configuration is `init`'s plus
a query file, owners and search columns:

<!-- source: docs/examples/api/rok-sqlc.toml -->
```toml
[api]
output = "src/features"

[api.owner]                  # each caller sees and changes only their own rows
projects = "owner_id"
tasks = "owner_id"

[api.search]                 # the columns the list's `q` matches
projects = ["name"]
tasks = ["title"]
```

Each feature serves these routes under `[api] prefix` (`/api/v1`) and its
route base (`/tasks`), and `[api.skip]` drops any of them:

| Route | Endpoint (`[api.skip]` name) | Answer |
|---|---|---|
| `GET /` `?page=&per_page=&q=&sort=&order=` (`q` with `[api.search]` columns) | `list` | `200` `{items, page, per_page, total}` |
| `POST /` | `create` | `201` with `Location` |
| `GET /{id}` | `get_one` | `200` |
| `PATCH /{id}` | `update` | `200`; with `If-Match` on a versioned table |
| `DELETE /{id}` | `remove` | `204`; `?permanent=true` on a soft-delete table |
| `POST /search` (`[api] search_endpoint = true`) | `search` | `200`, a page; body `{filter, sort, order, page, per_page}` |
| `POST /{id}/restore` (soft-delete tables) | `restore` | `200` |
| `GET /by-<column>/{value}` (single-column unique keys) | `lookups` | `200` |
| `GET /{id}?include=<name>`, `GET /{id}/<name>`, `PUT`/`DELETE /{id}/<name>/{other}`, `PUT /{id}/<name>` | `relationships` | `200`, `200` with a JSON array, `204`, `204` |

`/health/live` and `/health/ready` sit outside the prefix. Errors follow
one wire standard, `{"error": {"code", "message", "details"?}}`, with the
snake_case codes `bad_request`, `unauthorized`, `forbidden`, `not_found`,
`conflict`, `payload_too_large`, `validation_failed`,
`precondition_required`, `version_conflict` and `internal_error`.

The API documents itself. Every generated handler carries utoipa's
`#[utoipa::path]` (its tag is the route base, its operation id the
handler's name, its responses exactly the statuses it answers, each error
with `ErrorBody`, and `bearer_auth` when it needs a caller), every body
derives `ToSchema`, and `src/features/generated.rs` gathers them in
`GeneratedApiDoc`. The scaffolded `app.rs` serves the document at
`/api-docs/openapi.json` and Swagger UI at `/docs/`. Your hand-written
paths and schemas go in the scaffolded `src/openapi.rs`, whose `ApiDoc`
the generated document merges into:

<!-- source: src/init/templates/openapi.rs -->
```rust
#[derive(OpenApi)]
#[openapi(paths(), components(schemas()))]
pub struct ApiDoc;
```

Name a handler annotated with `#[utoipa::path]` in `paths(...)`, and a
schema no path reaches in `components(schemas(...))`. A project scaffolded
before the document adds `src/openapi.rs`, the routes in `app.rs` and the
`utoipa-swagger-ui` dependency by hand (the
[OpenAPI guide](docs/guide/openapi.md) lists the steps). `[api] openapi =
false` turns the document off, leaving generated output with no utoipa at
all; `init`'s `src/openapi.rs` and the document's lines in `app.rs` and
`lib.rs` are yours, so remove them by hand (the guide lists them, and
`rok-sqlc g` warns while `src/openapi.rs` uses `GeneratedApiDoc`).

The handlers call a generated service trait with a working default per
endpoint. A business rule overrides one method in the feature's
`service.rs`, which is scaffolded once and then yours:

<!-- source: docs/examples/api/src/features/tasks/service.rs -->
```rust
impl TasksServiceApi for TasksService {
    fn pool(&self) -> &PgPool {
        &self.pool
    }

    /// A task goes only into one of the caller's projects, and counts as
    /// one of its open tasks. Both writes share `conn`, so `create` commits
    /// them together.
    async fn create_in(
        &self,
        conn: &mut PgConnection,
        user: AuthUser,
        input: CreateTaskDto,
    ) -> Result<Task, AppError> {
        self.projects
            .task_opened(&mut *conn, user, input.project_id)
            .await?;
        let row = repo::create(&mut *conn, input.into_new(user.id)).await?;
        Ok(row)
    }
}
```

`[api]`'s keys are in the [configuration reference](#rok-sqlctoml), and the
next two sections document `init` and `check-arch`.

## Starting an API project: `rok-sqlc init`

`rok-sqlc init [DIR]` (default: the current directory) scaffolds the
actix-web application skeleton of ADR 0016 into a project. It generates
nothing; `rok-sqlc g` does that once there are migrations.

| File | What it is |
|---|---|
| `rok-sqlc.toml` | `schema = "migrations/"`, `derive = ["serde", "validate"]`, `extractors = ["actix_web"]`, `primary_key_ids = "uuid_v7"` and `api.output = "src/features"`, followed by the dependencies to add to `Cargo.toml`, as comments |
| `migrations/` | empty: your migrations go here |
| `src/lib.rs` | declares every module `pub`: the application is a library, so generated code it does not use yet never warns |
| `src/main.rs` | starts the server through the library (named after `Cargo.toml`'s package), nothing else |
| `src/app.rs` | the only wiring file: the pool, the generated `register_services` and `configure_all`, health, and the OpenAPI document at `/api-docs/openapi.json` with Swagger UI at `/docs/` |
| `src/openapi.rs` | `ApiDoc`, for your hand-written paths and schemas, and `document()`, which merges the generated `GeneratedApiDoc` into it |
| `src/config.rs` | `Config::from_env` (`DATABASE_URL`, `BIND_ADDR`, `JWT_SECRET`, pool settings), the only environment reader |
| `src/error.rs` | `AppError`, answered with the wire standard's error body, and the `sqlx` error mapping |
| `src/shared/mod.rs`, `src/shared/auth.rs` | the shared tools, and the `AuthUser` and `AdminUser` extractors (HS256 JWT bearer tokens) |
| `src/features/mod.rs` | `mod generated; pub use generated::*;` |
| `AGENTS.md` | the architecture rules, and where each piece of code goes |

Every file is a scaffolded file: it is written only when absent, starts
with `// Scaffolded once by rok-sqlc; this file is yours.`, and is never
rewritten. Running `init` again restores a deleted file and keeps every
other one as it is. Generation scaffolds files the same way (a feature's
`service.rs`): `--check` reports a missing one, never its contents, and a
scaffolded file is never stale.

One exception: run after `cargo new`, `init` replaces `src/main.rs` when it
is still cargo's untouched hello-world default (line endings and a trailing
newline aside), and prints `replaced cargo's default src/main.rs`. Any other
`src/main.rs` is kept.

### Starting from a template

| Flag | Meaning |
|---|---|
| `-t`, `--template <NAME>` | Copy this ready-made project instead of the skeleton. The only one is `actix`; any other name fails and lists the valid ones. |

`rok-sqlc init --template actix [DIR]` copies a complete actix-web project
(its configuration, migrations, scaffolded files, tests and README) into
`DIR`. The templates are built into the binary, so this works from
`cargo install`. Like the skeleton, each file is written only when absent,
and cargo's untouched default `src/main.rs` is replaced, so `DIR` can be
new or an existing cargo project. rok-sqlc's generated files are not
copied: run `rok-sqlc g` to generate them, as the printed next steps say.
The template's pinned `Cargo.lock` is copied when the project has none.
When the project already has a `Cargo.toml`, it is kept and the
template's Rust files name the project's library crate (`use
myapi::app` instead of `use actix_api::app`).

## Checking the architecture: `rok-sqlc check-arch`

`rok-sqlc check-arch` (`a`) checks an API project against ADR 0016's
architecture, the rules its `AGENTS.md` states. It reads `api.output` (the
features directory) and `api.db_path` (the data layer, default `crate::db`)
from `rok-sqlc.toml`, discovered like `generate` does or named with
`-c`/`--config`, and checks the project's `src/`. Each violation is printed
as `path:line: rule: message`, and any violation exits with code 1, for CI:

```text
src/features/notes/service.rs:3: rule-1: `actix_web::HttpResponse`: only routes.rs, handlers.rs, app.rs, main.rs, error.rs, features/generated.rs, shared/ and db/ may use actix_web
```

The layout checks (`layout`):

- a feature directory holds only `mod.rs`, `routes.rs`, `handlers.rs`,
  `dto.rs`, `model.rs`, `repo.rs`, `service_api.rs` and `service.rs`;
- no file or directory is named `utils`, `helpers` or `common`;
- `src/` has no top-level directory but the data layer's, `shared/`, the
  features directory's and `bin/`.

The rules, read from the Rust source with `syn` (comments, strings and
test code, `#[cfg(test)]` or `#[test]`, never count):

| Rule | What it allows |
|---|---|
| `rule-1` | `actix_web` only in a feature's `routes.rs` and `handlers.rs`, `app.rs`, `main.rs`, `error.rs`, the features' `generated.rs`, `shared/` and the data layer |
| `rule-2` | `sqlx` only in a feature's `repo.rs` and `model.rs`, `app.rs`, `error.rs`, the features' `generated.rs`, `shared/` and the data layer; a feature's `service.rs` and `service_api.rs` may name `sqlx::PgPool` and `sqlx::PgConnection` and nothing else |
| `rule-4` | a feature never refers to another feature's modules |
| `rule-5` | `shared/` never refers to the features module |
| `rule-6` | no `unwrap()`, `expect()` (as methods or called through a path, `Option::unwrap(x)`), `panic!`, `todo!`, `println!` or `dbg!` |
| `cross-feature-write` | a feature never refers to another table's `<db_path>::<table>::write`; reads are fine |

`-l`/`--lenient` prints layout violations as warnings on stderr instead of
failing; rule violations still fail. Generated code passes every check.

## Using it from `build.rs`

The library runs exactly what the CLI runs: `rok_sqlc::generate(&Config) ->
Result<Report>`. Add `rok-sqlc` under `[build-dependencies]`:

<!-- source: examples/build_script.rs -->
```rust
fn main() -> Result<(), Box<dyn Error>> {
    println!("cargo::rerun-if-changed=migrations");
    println!("cargo::rerun-if-changed=queries.sql");

    // Paths are relative to the package root, where Cargo runs build scripts.
    let mut config = rok_sqlc::Config::default();
    config.schema = vec!["migrations".into()];
    config.queries = vec!["queries.sql".into()];
    config.output = "src/db".into();

    match rok_sqlc::generate(&config) {
        Ok(_report) => Ok(()),
        Err(error) => {
            // The report says which tables and queries failed, and where.
            for failure in &error.report().table_failures {
                println!("cargo::warning={failure}");
            }
            for failure in &error.report().query_failures {
                println!("cargo::warning={failure}");
            }
            Err(error.into())
        }
    }
}
```

The library never reads `rok-sqlc.toml` and never prints: a build script gets
exactly the `Config` it built. Set `config.conventions`
(`rok_sqlc::Conventions::rok()`), `config.derive`
(`rok_sqlc::Derive::Serde`), `config.extractors` (`rok_sqlc::Extractor`),
`config.relationships`
(`rok_sqlc::RelationshipChange`), `config.modules` and `config.api`
(`rok_sqlc::ApiConfig::new`, with `ApiAccess` and `ApiEndpoint`) to match the config
file's sections.
`Config` is `#[non_exhaustive]`, so start from `Config::default()` and set
fields. The `Report` lists written, unchanged, refused and stale files and
any skipped tables or queries.

The stable library API is `generate`, `Config`, `Conventions`, `Derive`,
`Extractor`, `IdGeneration`, `RelationshipChange`, `ApiConfig`, `ApiAccess`,
`ApiEndpoint`, `Report` (with `RefusedFile`, `TableFailure` and
`QueryFailure`), and `Error`. Changing the *generated* API counts as a
breaking change too (see [ADR 0012](docs/adr/0012-library-api-and-stability.md)).

## CI with `--check`

`--check` regenerates in memory and compares the result with the files on
disk. It exits 1 and lists every missing, changed or stale file when they
differ, and it writes nothing:

```sh
rok-sqlc g --check
```

Run it in CI after installing rok-sqlc to catch migrations or queries that
were changed without regenerating.

Line endings don't count as drift. rok-sqlc reads migrations and query
files with CRLF as LF and writes `\n`, and it compares generated files the
same way. A checkout with CRLF line endings (Windows, `core.autocrlf`)
therefore generates the same code and passes `--check`.

## Supported SQL and type mapping

rok-sqlc reads PostgreSQL DDL with a SQL parser. It never connects to a
database.

| PostgreSQL | Rust |
|---|---|
| `SMALLINT`, `INT2`, `SMALLSERIAL` | `i16` |
| `INTEGER`, `INT`, `INT4`, `SERIAL` | `i32` |
| `BIGINT`, `INT8`, `BIGSERIAL` | `i64` |
| `REAL`, `FLOAT4` | `f32` |
| `DOUBLE PRECISION`, `FLOAT8`, `FLOAT` | `f64` |
| `BOOLEAN` | `bool` |
| `TEXT`, `VARCHAR`, `CHAR` | `String` (`&str` for parameters) |
| `UUID` | `uuid::Uuid` |
| `DATE` | `chrono::NaiveDate` |
| `TIME` | `chrono::NaiveTime` |
| `TIMESTAMP` | `chrono::NaiveDateTime` |
| `TIMESTAMPTZ` | `chrono::DateTime<chrono::Utc>` |
| `TIME WITH TIME ZONE`, `TIMETZ` | `sqlx::postgres::types::PgTimeTz` |
| `INTERVAL` | `sqlx::postgres::types::PgInterval` |
| `BYTEA` | `Vec<u8>` (`&[u8]` for parameters) |
| `NUMERIC`, `DECIMAL` (at most 28 digits) | `rust_decimal::Decimal` |
| `MONEY` | `sqlx::postgres::types::PgMoney` |
| `INT4RANGE`, `INT8RANGE` | `sqlx::postgres::types::PgRange<i32>`, `PgRange<i64>` |
| `NUMRANGE` | `sqlx::postgres::types::PgRange<rust_decimal::Decimal>` |
| `DATERANGE`, `TSRANGE`, `TSTZRANGE` | `sqlx::postgres::types::PgRange<T>` of the `chrono` type above |
| `INET`, `CIDR` | `ipnetwork::IpNetwork` (SQLx's `ipnetwork` feature) |
| `MACADDR` | `mac_address::MacAddress` (SQLx's `mac_address` feature) |
| `JSON`, `JSONB` | `serde_json::Value` |
| `T[]` | `Vec<T>` |
| `CREATE TYPE … AS ENUM` | an enum in `db::types` |
| text column with `CHECK (col IN ('a', …))` | an enum in `db::types` (`InvoiceStatus`) |

A nullable column is wrapped in `Option`, and a primary key column uses its
typed id. SQLx implements no `PartialOrd` for `PgInterval`, `PgTimeTz`,
`PgMoney` or `PgRange`, so those columns get equality filters, as `BYTEA`
and network columns do. `PgTimeTz` holds
`chrono` types, or the `time` crate's types when SQLx's `time` feature is on.
SQLx decodes `INTERVAL` only from prepared statements, which is what the
generated code uses.

**Statements rok-sqlc reads:**

- `CREATE TABLE`: columns, `DEFAULT`, identity and `GENERATED` columns,
  inline and table-level `PRIMARY KEY`, `UNIQUE`, `REFERENCES`/`FOREIGN KEY`,
  and value-list `CHECK`s. Other `CHECK`s are ignored.
- `ALTER TABLE`: `ADD COLUMN`, `DROP COLUMN`, `RENAME COLUMN`,
  `ADD CONSTRAINT` (primary key, unique, foreign key, value-list check;
  other `CHECK`s are ignored, as in `CREATE TABLE`),
  `ENABLE`/`DISABLE ROW LEVEL SECURITY`, and `ALTER COLUMN` with
  `[SET DATA] TYPE` (with or without `USING`), `SET`/`DROP NOT NULL`,
  `SET`/`DROP DEFAULT`, and `ADD GENERATED … AS IDENTITY`. The column ends up
  in its final shape, and its keys follow a type change. `DROP IDENTITY` and
  `DROP EXPRESSION` act like `DROP DEFAULT`, and `TYPE … COLLATE` like
  `TYPE`. `RENAME CONSTRAINT` renames a primary key or unique constraint.
- `ALTER TABLE` clauses that leave the model as it is: `SET STATISTICS`,
  `SET STORAGE`, `SET COMPRESSION`, `SET`/`RESET (…)`, `SET GENERATED`,
  `RESTART` and other identity options on a column; `SET`/`RESET (…)`,
  `CLUSTER ON`, `SET WITHOUT CLUSTER`, `SET TABLESPACE`, `SET [UN]LOGGED`,
  `[NO] FORCE ROW LEVEL SECURITY`, `REPLICA IDENTITY`, `OWNER TO`,
  `ENABLE`/`DISABLE TRIGGER`/`RULE`, `VALIDATE CONSTRAINT` and
  `ALTER CONSTRAINT` on the table.
- `ALTER INDEX`, `ALTER SEQUENCE`, `ALTER VIEW` and `ALTER MATERIALIZED
  VIEW … RENAME TO`, for the names PostgreSQL gives unnamed constraints.
  Renaming a key constraint's index renames the constraint.
- `CREATE UNIQUE INDEX` on plain columns, which becomes a unique key with a
  lookup. A partial index over live rows (`WHERE deleted_at IS NULL`) counts
  under the soft-delete convention. Expression indexes are ignored.
- `CREATE TYPE … AS ENUM`, and `ALTER TYPE … ADD VALUE`/`RENAME VALUE`/
  `RENAME TO`. A renamed enum takes the Rust name of its new name, and the
  columns using it follow.
- `DROP TABLE`, which removes the table, so its generated files become stale
  and are removed. Foreign keys other tables hold to it go too, as with
  `CASCADE`: those columns keep their raw type and lose the relationship.
- `DROP TYPE` of an enum. With `CASCADE`, the columns using it are dropped.
  Without it, a table that still uses the type fails.

All other statements (functions, triggers, policies, views, grants, and so
on) are skipped without comment, including functions and procedures with a
`BEGIN ATOMIC` body and `DO` blocks. Schema qualifiers are
kept (`catalog.products`), and `public.` is the same as no qualifier.

**What is rejected, and why.** Generation is strict by default
([ADR 0001](docs/adr/0001-strict-generation-by-default.md)): if a table or
query can't be generated correctly, the run writes nothing and exits 1, and
the error is reported as `path:line:`. A silently incomplete `db` module is a
worse failure than a loud one. `--lenient` skips the offending tables and
queries with warnings instead. A skipped table keeps the files an earlier run
generated for it, unchanged and still declared in `mod.rs`; they are not
stale, so `--check` reports the warning but no drift. The rest is generated
against the table's last good shape (before the migration that broke it), so
its enums, typed ids, and relationships stay and the crate still compiles.
A table that fails at its own `CREATE TABLE` has no such shape, and its old
files are removed as stale. If every table is unsupported, the run still
fails. With `--resource`, only that table's problems count.

| Rejected | Why |
|---|---|
| Column types not in the table above (`POINT`, `XML`, `MACADDR8`, multiranges, …) | There is no chosen Rust mapping yet, and rok-sqlc doesn't guess one. |
| `INTERVAL`, `TIME WITH TIME ZONE`, `MONEY` and range types with `derive = ["serde"]` | SQLx's `PgInterval`, `PgTimeTz`, `PgMoney` and `PgRange` implement no serde traits, so the serde derives wouldn't compile. The whole run fails, even with `--lenient`. |
| `NUMERIC(p, s)` with `p` > 28 | `rust_decimal` holds 28 significant digits, so the value would fail to decode at runtime. |
| Other `ALTER TABLE` clauses (`RENAME TO`, `ALTER COLUMN … TYPE` to an unsupported type, `DROP NOT NULL` on a primary key column, …) | The table's shape after the change is unknown, so the table fails. |
| An `ALTER TYPE` that can't be applied (an existing label or type name, an unknown label) | The tables that use the type fail. |
| A table whose module name is reserved or already taken | Its module would collide with a generated one. Rename it in `[modules]`. |
| Two typed ids of one name imported into one file, or an imported id named like one of the file's own items | The generated code wouldn't compile. Rename a module in `[modules]`. |
| Columns whose filter or sort-key names collide (`weight` next to `weight_is_null`) | The generated code wouldn't compile. |
| Two relationships of one table with the same name, or a relationship named like a filter field | Rename one in `[relationships]`. |
| A soft-delete column that is not a nullable timestamp | `delete` couldn't record the time. |
| A query placeholder or result expression rok-sqlc can't type | Add a `-- param:` or `-- column:` override. |
| Unknown tables or columns in a query, more than one statement, `UNION` outside a recursive CTE, data-modifying CTEs | They can't be analyzed (yet). |
| A recursive CTE whose recursive term returns other columns than its anchor | The CTE's columns come from the anchor. |
| An `ON CONFLICT (cols)` target that is not a unique key | It would fail at runtime. The error lists the table's unique keys. A partial unique index counts when the target repeats its condition: `ON CONFLICT (email) WHERE deleted_at IS NULL`. |
| An `ON CONFLICT ON CONSTRAINT name` that names no primary key or unique constraint | It would fail at runtime. The error lists the table's constraint names. |

## Limitations and roadmap

**Known limitations:**

- Types outside the type table (`POINT`, `XML`, `MACADDR8`, multiranges, …)
  are unsupported, in tables and in query casts (`$1::point`).
- `INTERVAL`, `TIME WITH TIME ZONE`, `MONEY` and range columns can't be
  generated with `derive = ["serde"]`.
- A partial-index `ON CONFLICT` target must repeat the index's condition
  exactly. PostgreSQL also infers a partial index from a condition that
  implies it, which rok-sqlc doesn't check.
- Relationship filters nest at most `MAX_RELATIONSHIP_DEPTH` (4) deep. Deeper
  filters make `search` fail with `sqlx::Error::InvalidArgument`.
- Keyset pagination (`search_after`) follows primary-key order only. Array
  and JSON columns get only null checks in filters.
- `UNION` is read only as the body of a recursive CTE, and data-modifying
  CTEs are rejected in query files.
- `ALTER TABLE … RENAME TO`, `SET SCHEMA`, partitioning (`ATTACH`/`DETACH
  PARTITION`), `DROP CONSTRAINT`, and other `ALTER TABLE` forms that change
  the model in ways rok-sqlc doesn't follow fail the table they alter, at
  their `path:line` (`--lenient` skips it). Any other statement the parser
  can't read stops the run at its `path:line`, unless it is a function,
  procedure, `DO` block, or `ALTER` of an index, sequence or view.
- Triggers are followed through `CREATE` and `DROP TRIGGER` only:
  `DISABLE TRIGGER` doesn't take a managed column's source of values away.
- Typed ids and relationships cover only the tables generated together. A
  foreign key into another migration set keeps its raw type and makes no
  relationship.
- A table `--lenient` skips is kept only with a last good shape: its model
  before the statement that broke it, which matches its kept files when
  the run that wrote them saw the migrations up to that statement. A table
  that fails at its own `CREATE TABLE` (an edited migration, say) has none,
  so its earlier files are removed as stale.
- Default constraint names follow renamed indexes, sequences, views and key
  constraints, but foreign key and check constraint names aren't tracked.
- A versioned `update` of a row that a concurrent transaction deletes while
  the `UPDATE` waits for its lock reports `VersionConflict`. A retry reports
  `NotFound`.

**Not planned** (possible later):

- Full-text search, pgvector, and embedding persistence.
- A compile-time-checked `query!` mode.
- Declared has-many-through and polymorphic relationships, beyond renaming
  and opting out of inferred ones.
- Nested writes (creating a row together with its children).
- Machine-readable output (`--format json`).
- SQLx versions other than 0.9, a user-facing module-directory input layout,
  and databases other than PostgreSQL.
- JSONB operators in typed filters.

## Contributing

```sh
cargo test                                   # unit, CLI, and generated-code suites
cargo clippy --all-targets -- -D warnings
cargo fmt --all -- --check
```

- **Two toolchains.** The tool builds on Rust 1.88 (so no `if let` guards in
  `match`, for example). The suites that compile generated code
  (`tests/fixture_compile/`, `tests/module_fixtures/`, and
  `the_examples_compile` in `tests/readme.rs`) need Rust 1.94. Below that,

  smoke-run the module fixtures in `modules/`. The module run creates
  databases, so the role needs `CREATEDB`. Without the variable, those tests
  print "skipping".
- **This README.** `tests/readme.rs` checks that every flag, alias and config
  key in the code appears here (and nothing else does), that every config
  sample is accepted, and that every code sample is copied verbatim from
  [`docs/examples/`](docs/examples/). It also checks that those examples have
  no drift and that they compile. After changing the generator, run
  `rok-sqlc g` in each example directory and update the samples here.
- **Decisions** are recorded as ADRs in [`docs/adr/`](docs/adr/). Read the

  reverse. [`docs/design.md`](docs/design.md) is the original design

- **Releases.** Bump `version` in `Cargo.toml`, move CHANGELOG's Unreleased

  `Cargo.toml`, builds the binaries, publishes the GitHub release with that
  CHANGELOG section as its notes, and then installs it with both install

  the tag.
