# AGENTS.md

One crate, folders by feature, a fixed set of files per feature, six rules.
Humans and code generators follow this file exactly. If a rule gets in your
way, change the rule here first, then the code.

`rok-sqlc g` generates the data layer (`src/db/`) and one API feature per
table (`src/features/<table>/`) from `migrations/`. Generated files start
with `// @generated by rok-sqlc` and are rewritten on every run: never edit
them. Scaffolded files start with `// Scaffolded once by rok-sqlc` and are
yours: rok-sqlc writes them once and never touches them again.

## Layout

```
src/
├─ lib.rs         declares every module `pub`: the application is a library
├─ main.rs        starts the server through the library. Nothing else.
├─ app.rs         builds AppState and the router, serves it with the mail sender (the ONLY wiring file)
├─ config.rs      reads env vars into one Config (the ONLY env reader)
├─ error.rs       AppError and its HTTP mapping, shared by all features
├─ db/            generated data layer: rows, typed ids, enums, all SQL, pool.rs
├─ shared/        tools with no business meaning (auth.rs, security/, mail/
│                 and rate_limit/ are yours; response, pagination, validation,
│                 tenant, health are generated)
└─ features/
   ├─ mod.rs        `mod generated; pub use generated::*;` plus hand-written features
   │                (`account`, `auth`: the generated layout, without model/repo)
   ├─ generated.rs  generated: declares the features; `Services`, `register_services` and `routes`
   └─ <feature>/
      ├─ mod.rs          generated: re-exports routes, the service and the trait
      ├─ routes.rs       generated: URL to handler
      ├─ handlers.rs     generated: parse, call one service method, return
      ├─ dto.rs          generated: request/response shapes and validation
      ├─ model.rs        generated: re-exports the rows and typed ids from db
      ├─ repo.rs         generated: re-exports the table's db functions
      ├─ service_api.rs  generated: the service trait, with a default per endpoint
      └─ service.rs      yours: the service struct and your overrides (business rules)
```

No other file may be added to a feature, and no file or directory anywhere
under `src/` may be named `utils`, `helpers` or `common`. Something that
doesn't fit is either a `shared/` tool (no business meaning) or belongs in
a feature.

The tree shows the default paths: `api.output` in `rok-sqlc.toml` moves the
features directory and `api.db_path` names the data layer's module, and the
rules below follow them.

## Where does each piece of code go?

| I am writing... | It goes in | Never in |
|---|---|---|
| A business rule | the feature's `service.rs`, overriding a `service_api.rs` default (`create_in`, `update_in`, ...) | handler, repo |
| A new endpoint, request or response shape | the schema and `rok-sqlc.toml` (`[api]`), then `rok-sqlc g` | generated files |
| SQL query | the data layer: a migration and `rok-sqlc g`, or the feature's query file, `queries/<feature>.sql` | service, handler |
| New DB table or column | `migrations/000N_name.sql`, then `rok-sqlc g` | anywhere else |
| Error case | a variant in `error.rs` | feature folder |
| Code two features need | `shared/` | one feature |
| Call to an outside system | `shared/<name>.rs` behind a trait | service directly |
| Env variable | `config.rs` | `std::env` anywhere else |
| Background or slow work | an outbox row written by `service.rs`, handled by a worker | request path |
| Writing another feature's data | a port (trait) declared in your `service.rs`, implemented in `app.rs` with the other service's `_in` method | that feature's files |
| Register a hand-written feature | `features/mod.rs` and `app.rs` | — |

## The six rules

1. In a feature, only `routes.rs` and `handlers.rs` use `axum`. Outside
   the features, so may `app.rs`, `main.rs`, `error.rs`, the features'
   `generated.rs`, `shared/` and the data layer.
2. In a feature, only `repo.rs` and `model.rs` use `sqlx`, and `service.rs`
   and `service_api.rs` may name `sqlx::PgPool` and `sqlx::PgConnection` and
   nothing else. Outside the features, so may `app.rs`, `error.rs`, the
   features' `generated.rs`, `shared/` and the data layer.
3. `service.rs` never writes SQL. It calls the data layer's functions and
   traits from `shared/`.
4. A feature never refers to another feature's modules. It may read any
   table through the data layer. It writes its own table through
   `<db_path>::<table>::write`, any table through its own query module,
   `<db_path>::queries::<feature>`, and another feature's data through that
   feature's service, behind a port it declares itself, inside the caller's
   transaction. It never calls another table's `write` or another feature's
   query module. The data layer is exempt: the schema crosses features.
5. `shared/` never refers to the features.
6. No `unwrap()`, `expect()`, `panic!`, `todo!`, `println!` or `dbg!`. Every
   fallible function returns `Result<_, AppError>`.

The features are the directories under `api.output` (`src/features/` by
default), and the data layer is the module `api.db_path` names (`crate::db`,
in `src/db/`, by default). `rok-sqlc check-arch` checks rules 1, 2, 4, 5 and
6 and the layout: a feature directory holds only `mod.rs`, `routes.rs`,
`handlers.rs`, `dto.rs`, `model.rs`, `repo.rs`, `service_api.rs` and
`service.rs`; no file or directory is named `utils`, `helpers` or `common`;
and `src/` has no top-level directory but the data layer's, `shared/`, the
features' and `bin/`. Test code is exempt from every rule: files under
`#![cfg(test)]`, items under `#[cfg(test)]`, `#[test]` and `#[<path>::test]`
functions, and `tests/`, which is not read. Each violation prints as
`path:line: rule: message`. Rule 3 is yours to keep.

Handlers are thin: parse, call one service method, return. One service
method does one thing; name it as a verb. DTOs are separate from rows, and
a response never carries a secret (`[api.hidden]`). Money is integer minor
units, time is UTC, and ids are UUIDs.

## Accounts

`features/auth/` (sign-up, sign-in, email verification, the password
flows, email change, invitations) and `features/account/` (`/auth/me`,
`/users/me`) are hand-written and follow the rules above. Keep to how
they work:

- **SQL.** `auth`'s goes in `queries/auth.sql`, `account`'s in
  `queries/account.sql`; SQL `shared/` runs goes in a file named after no
  feature (`queries/session.sql`, `queries/mail.sql`). Run `rok-sqlc g`
  after editing one.
- **Mailed links.** A token purpose (the `auth_tokens.purpose` check), an
  arm in `link_kind` (lifetime and message) in `auth/service.rs`, and a
  `Templates` method in `shared/mail/templates.rs`. Issue and mail it with
  `mail_link` on the flow's transaction, commit with `outbox.commit(tx)`,
  and redeem it with `consume_token`. Never store or log a raw token.
- **Answers.** A body of the wrong shape is `422` (the DTO's rules); a flow
  refusing a well-formed request is `400` with `AppError::InvalidToken`,
  `WrongPassword` or `BreachedPassword`. Don't tell a caller whether an
  email has an account where the flow answers `202`.
- **Sessions.** A change that must sign a user out bumps
  `users.token_version`; disabling sets `is_active = false`. `AuthUser`
  checks both on every request.
- **Routes.** New `/auth` routes go in `auth::routes`'s scope, so the rate
  limit covers them, and in `ApiDoc`'s `paths(...)`.
- **Tests.** Drive each flow over HTTP in `tests/`, with `mailed` and
  `mailed_token` from `tests/support/mod.rs`.

## Uploads

`features/media/` (`/api/v1/media`) is hand-written too. Bytes go through
the `Storage` port in `shared/storage/` (`AppState.storage`): put, get and
delete by a key the feature generates (`media/<uuid>`), never one a caller
sends. A file's type is detected from its bytes, never taken from the
request. Tests store in memory; swap in your own with
`AppState::with_storage`.

Profile photos (`features/account/`, `PUT`/`DELETE /users/me/avatar`)
use the same port under `avatars/<random>.jpg`. `shared/thumbnail.rs`
decodes (JPEG, PNG, WebP, under size limits), crops and re-encodes them
on a blocking thread. `users.avatar_url` is a generated column
(`migrations/0005_avatars.sql`), so every user response, the generated
`users` feature's included, answers it.
